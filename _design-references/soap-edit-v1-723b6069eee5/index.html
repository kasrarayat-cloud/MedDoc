SOAP edit — ten interaction directions v1

Kasra reports the current click‑to‑edit flow is “very hard.” Below: a diagnostic of why it likely feels that way, then ten static mockups exploring different ways to ask “edit” of a SOAP section. Each pattern shows three frames — view, trigger, active edit — and a one‑line win/cost tag.

Current flow — SoapInlineEdit.tsx

What clicking a SOAP section does today

Each section body is a <button> wrapping the rendered markdown. Hover lights a subtle background and reveals a mono “Click to edit” hint with a pencil glyph. Click swaps the body for a single <textarea> with a sage outline and a footer that reads “Esc / blur saves.” Either key path (or any click outside the textarea) commits the edit via saveSoapDraftAction against the visit’s soapVersion optimistic‑lock; failure leaves the textarea open with a toast.

Friction — three things the code makes hard

Why doctors call it “very hard”

  1. Section ≠ scope. The textarea contains the entire SOAP markdown blob, not just the section you clicked (SoapInlineEdit.tsx : 13–17). You meant to fix one line in Plan; you’re looking at 300 lines covering S, O, A and P.
  2. Blur silently saves. Any click outside the textarea — the coding rail, the Rx warnings, whitespace — fires onBlur → persist(draft). There is no explicit Save or Cancel chrome; accidental commits are one stray click away.
  3. Esc saves, not cancels. Esc calls the same persist(draft) as blur. The control that every other app uses for “throw this away” here means “commit and exit.” There is no revert path — undo is up to the browser’s own undo stack, which doesn’t survive the save round‑trip.

Voice‑first edit

Each section header carries a small mic. Click to dictate “Add to Plan: order chest X‑ray.” The system streams a tentative paragraph the doctor approves with Save; textarea drop‑down is the typed fallback. Aligned with the app’s existing voice‑dictation input mode.
