# Prospective checked source interpretation

Version 4 form definitions enumerate the required parts of each original answer
destination. Two preparation roles propose and check the complete form; a clinician
reviews the resulting definition version before use. Component edits remain drafts
until whole-form review. Original questions, physical locators, Word bytes and
previous approved versions are retained.

New version 4 generations use `source-assertion-graph-v25`. An extractor supplies
exact source facts, typed assertions, explicit relationships, exhaustive source-unit
coverage and practitioner time accounts. An independent checker rereads the original
source, every assertion and relationship, all source units, and every requested
component and rendered answer. Exact spans, registry identity, calendar dates,
numeric values, units, scales and physical destination constraints remain mandatory.
Structural validity alone does not establish clinical meaning.

Unknown interpretation, actual contradiction, assignment omission, extraction error
and definition error remain distinct outcomes. A hold records its initiating rule,
exact evidence, affected assertions and destination. Only an explicit validity
dependency propagates a source hold. Descriptive causation does not establish that
an independently true dependent fact is false. An incomplete E/M time account
holds its billing consumer; it does not retract a separately confirmed clinical
time total. Source corrections and retractions still govern their actual dependents.

The normal path uses extractor, assigner and checker once. A second assignment and
check are permitted only for a repairable assignment error involving changed
selections of already eligible facts. Extraction and interpretation disagreements
remain review outcomes; the worker does not rerun the same assignment to claim
they were repaired. The existing maximum is five clinical provider stages.

One append-only `SourceInterpretation` row binds a succeeded generation to its
patient, department, encounter, service date, form version, original source, approved
definitions, exact requests, raw responses and derived answers. Reload and export
verify this retained lineage. Explicit clinician edits keep the original generated
answer and all attributed, dated prior decisions. A server signature binds the
complete manual answer and history; ordinary signing-key fallbacks support rotation.
Retain the original signing key in encrypted recovery material. Before rotating it,
configure Django's `SECRET_KEY_FALLBACKS` and verify existing manual decisions;
discarding the old key without its fallback invalidates their signatures.
These edits never become evidence of automatic clinical-generation correctness.

New Corti coding runs consume this same checked interpretation. ICD ownership,
event scope, relevance and certainty come from checked assertions. Exact literal
nominal references identify the condition and its separately qualified modifiers;
they are distinct from the broader text retained for clinical display. Positive
and negative claims retain their checked polarity through classification. Dated
Index matching does not reinterpret their surrounding narrative to decide truth.
These occurrences still require the service-date Index/Tabular route and
specificity checks. Durations and other ancillary facts do not create extra disease
obligations. Unresolved or competing routes remain explicit; partial coverage cannot
be marked complete. Practitioner-time review uses the same explicit account with
its separate bounded criteria and clinician attestation. The graph supplies no
licensed CPT descriptions, edition verification, or MDM criteria.

Historical contracts, raw results, approvals and failed encounters are not upgraded
or rewritten. Version 4 requires a separately reviewed definition version. Existing
coding engines and historic run configurations remain pinned; this prospective
checked coding path requires the existing Corti integration.
Any future change to this contract's derivation requires a new prospective contract
and preservation of the reader used by existing retained interpretations.

Verification distinguishes actual retained-response replay, constructed boundary
controls, frozen independent cases, and fresh installed HTTPS acceptance. Their
counts must not be combined into a claim of general natural-language reliability.
Native Microsoft Word pagination and licensed CPT descriptor/edition acceptance
remain separate requirements. Local tests alone do not establish live acceptance.

## Encounter scope for prospective components

New version 4 preparations pin `semantic_component_contract=field-components-v2`.
Every component explicitly chooses `encounter_scope`: `current`, `past`, or
`all_documented`. This is independent of its subject, event temporality and
polarity. A future plan documented in the current encounter remains a future plan;
neither the encounter permission nor a supported clinical answer makes it a
performed service or a current disease.

An open topic requesting all documented symptom negatives uses one complete topic
component with `all_documented`. Its answer may contain current-encounter facts,
explicit past-encounter/past-event facts, or both. It does not require an invented
finding in every time category. Unknown and future encounter ownership remain
held. Selected past roots must retain their exact established timing evidence;
null or omitted timing evidence cannot be hidden by an all-documentation scope.
All ownership, negation, qualifier, independent-check and required-sibling gates
remain in force. Current ICD and E/M eligibility remain separate and unchanged.

Both preparation roles receive the closed v2 schema. The ordinary component editor
displays encounter scope separately from event time and saves it in the signed,
revision-bound draft. The complete form still requires review and approval. Source
questions, Word bytes, physical destinations and prior definitions are unchanged.

A missing preparation config key retains `field-components-v1`. Its validator,
scope rule, provider instructions, request envelopes and restore behavior remain
the historical branch. New encounter instructions apply only to approved v2
definitions. Existing approvals are never silently upgraded; choosing v2 requires
a new prospective preparation and approval. The factual graph schema is unchanged.

## Bounded definition output capacity

New version 4 preparations using `field-components-v2` on the existing supported
Anthropic model pin `bounded-definition-output-32k-v1`: at most 32,000 output
tokens and 240 seconds per role, two role calls and the unchanged 512,000-byte
complete-request bound. The immutable two-call quote is recalculated before any
send. This addresses the larger component schema exhausting the older output
limit; it does not make truncated or invalid JSON acceptable.

Preparations without the explicit capacity profile retain their original
16,000-token, 120-second limits, quote and request envelope, including earlier
version 4 preparations. Unknown profiles, mismatched limits and unsupported
provider/model contracts are refused. Migration 0035 changes only the definition
capacity admission condition in the existing immutable stage guard; predecessor,
lineage, ownership, metering and two-call checks remain in force. There is no
historical backfill, provider switch or automatic retry. A failed preparation and
its raw response remain retained; a replacement requires the existing explicit
new-attempt route. Fresh installed acceptance remains a separate requirement.
