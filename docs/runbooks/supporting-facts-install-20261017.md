and browser verification. `python -B -m ops.activate_supporting_facts` is inert
without `--execute`. Do not rerun consumed activation controllers or plans.

templates, static assets, migrations, settings, provider policies, output

Failure receipts retain the exact operation stage, exception class, validated
SQLSTATE, fixed connection-failure classification and operator source locations.
They never copy exception messages, SQL, credentials or clinical source text.
An absent SQLSTATE is recorded as null; a classification cannot establish a
root cause the exception did not reveal. Before any source-publication attempt,
failure may resume the original release only after verifying the base HEAD,
clean tracked working tree and index, original environment, each prepared file
proof and absence of new source paths. Once publication is attempted, automatic
original-release recovery is forbidden even if Git still reports the base HEAD:
a failed fast-forward can already have changed the index and runtime files.
If any check fails after new services begin starting, the operator attempts to
stop every owned unit and verifies every unit is inactive while retaining the
coordination locks. The failure receipt records stop/verification failures
honestly; it does not claim shutdown when that cannot be verified. Stopped units
stay stopped for diagnosed recovery. The operator never retries, overwrites an
attempt or rolls back clinical state.
Strict database/file equality ends before services resume.
