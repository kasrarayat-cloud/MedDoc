## P1 cluster — 3 audit-row gaps under HIPAA §164.312(b)

The agent caught a meaningful pattern across the 5 newly-deep pages:
**three distinct PHI-adjacent surfaces lack the audit-row instrumentation
the rest of the product has shipped.** Round 3 PR-C (which closed the
read-side audit gaps for `/visits/[id]`, `/patients/[id]`, and the
visits + patients list pages) didn't reach these three.

### Finding F-09 — `/dashboard` reads PHI without `VIEWED_*` audit rows

- **Severity:** P1 (§164.312(b) compliance gap on the most-trafficked
  authenticated page; not a doctor-facing blocker, but auditable in a
  HIPAA review)
- **Page / file:** `apps/transcribe-md/src/app/dashboard/page.tsx`
- **What's missing:** `DashboardBody` fans out 6 parallel queries
  against `transcribe_md_patients` + `transcribe_visits` + others.
  Round 3 PR-C added `logAudit({ action: 'VIEWED_PATIENT_LIST' })`
  to `apps/transcribe-md/src/app/patients/page.tsx:99`,
  `VIEWED_VISIT_LIST` to `apps/transcribe-md/src/app/visits/page.tsx:137`,
  and equivalents to the API routes — but `/dashboard` reads the same
  surfaces directly via Prisma and writes ZERO audit rows.
- **Why P1:** `/dashboard` is the post-login landing page; every doctor
  hits it on every session. The audit log under-reports PHI access by
  one row per session per doctor.
- **Walker observability:** `sweep-dashboard.mjs` captures the audit
  baseline empirically. When the page loads cleanly, the `audit-baseline`
  event reports `delta: 0` — the v3.3 classifier should surface that
  delta-0-on-PHI-read combination as a Pattern-D finding.
- **Recommended fix scope:** small (3 LOC at the top of `DashboardBody`).
  Call `logAudit({ action: 'VIEWED_PATIENT_LIST', ... })` and
  `logAudit({ action: 'VIEWED_VISIT_LIST', ... })` once per render.
- **Escalate to:** none — fix inline.

### Finding F-10 — Visit creation has no `VISIT_CREATED` audit action

- **Severity:** P1 (§164.312(b) write-side gap; the agent saw it because
  there's no enum value to map a click to)
- **Page / file:** `apps/transcribe-md/src/app/visits/new/page.tsx`
  (server action that creates `transcribe_visits` row) +
  `apps/transcribe-md/src/lib/audit.ts` (enum)
- **What's missing:** `AuditAction` enum has `TM_PATIENT_CREATED`
  (for inline patient creation) but no `VISIT_CREATED` /
  `VISIT_QUEUED`. A new visit row gets inserted into
  `transcribe_visits` without any audit row marking the creation.
  `VIEWED_VISIT` fires later when the doctor navigates to the visit,
  but the create-event itself is invisible.
- **Why P1:** Pattern A — silent write. Auditors reviewing the trail
  see "user X viewed visit Y at time T" but no record of how Y came to
  exist or who created it. Adjacent fix to F-09.
- **Recommended fix scope:** small (add enum value + `logAudit()` call
  in the server action). Mirror PR #134's `EM_OVERRIDE_APPLIED` shape.
- **Escalate to:** none — fix inline.

### Finding F-11 — `/settings` reads `user_sessions` (IP + UA) without audit

- **Severity:** P1 (the strongest case of the three — `user_sessions.ipAddress`
  and `userAgent` are device-fingerprint columns; PHI-adjacent under a
  strict §164.312(b) reading)
- **Page / file:** `apps/transcribe-md/src/app/settings/page.tsx`
  (Sessions section reads + renders the active sessions table)
- **What's missing:** No `VIEWED_SETTINGS` action in the enum.
  Settings reads `users.email/specialty/npi/clinicName/timeZone` AND
  `user_sessions.ipAddress/userAgent` — the latter is enough to
  fingerprint a doctor's device. Currently a clean read with zero
  audit instrumentation.
- **Why P1:** Compliance — §164.312(b) covers any PHI-adjacent read.
  Device fingerprints fit the "discoverable through a session record"
  test even if not strictly PHI.
- **Recommended fix scope:** small. Add `VIEWED_SETTINGS` enum +
  `logAudit({ action: 'VIEWED_SETTINGS' })` at top of the page server
  component.
- **Escalate to:** none — fix inline. (Worth pairing with F-09 + F-10
  in a single "Round 3 PR-C follow-up" PR.)

## P2 cluster — UX edge cases

### Finding F-12 — Dashboard `<Suspense>` boundary swallows render errors

- **Severity:** ~~P2~~ → **CLOSED-AS-NAB** (false positive in v3.2 discovery)
- **Page / file:** `apps/transcribe-md/src/app/dashboard/page.tsx`
- **What the discovery sub-agent claimed:** `DashboardBody` is the only
  child inside `<Suspense>`. Its `Promise.all` of 6 parallel queries
  can fail (Prisma reconnect, query-timeout, transient infra issue)
  and bubble up to the boundary; there's no `error.tsx` or
  `<ErrorBoundary>` peer. Result: skeleton shows forever.
- **What investigation found** (2026-05-06, branch
  `fix/dashboard-suspense-error-boundary`): the claim is **wrong**.
  The sub-agent missed the sibling `apps/transcribe-md/src/app/
  dashboard/error.tsx`. Next.js auto-wraps `page.tsx` in a React
  Error Boundary when a sibling `error.tsx` exists in the same route
  segment. So:
    - When `<DashboardBody>` throws (or its `Promise.all` rejects),
      the throw propagates up through Suspense.
    - Next.js's segment-level Error Boundary catches it.
    - `dashboard/error.tsx` mounts the shared `<ErrorFallback>` with
      `scope='dashboard'`, which renders the
      "Something went wrong" UI + a stable error ID + a `Try again`
      button (wired to Next's `reset()` to re-render the subtree) +
      a "Back to dashboard" link + sends telemetry to
      `/api/client-errors` for ops visibility.
    - The skeleton is replaced with the error UI, NOT left forever.
- **What WAS missing:** no test proved the chain. A future refactor
  (e.g. moving `<Suspense>` outside the error.tsx scope, or
  accidentally deleting `dashboard/error.tsx`) could regress without
  CI tripping. The PR fixes that by adding 6 unit tests in
  `apps/transcribe-md/tests/error-boundary/dashboard-error.test.tsx`
  that pin:
    - `DashboardError` renders the "Something went wrong" heading
    - retry button is wired to `reset()`
    - error digest renders as a stable error ID
    - raw `error.message` is **not** leaked into the UI (PHI safety)
    - "Back to dashboard" link href = `/dashboard`
    - sendBeacon fires to `/api/client-errors` with `scope='dashboard'`
- **Outcome:** F-12 closed as NAB. No product code changed; tests
  added so the NAB stays NAB across future refactors.
- **Discovery-report process improvement:** the sub-agent's
  enumeration of the dashboard's interactive elements should have
  included a check for the sibling `error.tsx` + `loading.tsx` files
  before flagging "no error boundary." A future v3.3 walker upgrade
  could enumerate route-segment files alongside DOM elements.

## P3 cluster — code-quality / future-risk

### Finding F-13 — `openCmdK()` synthetic-keydown TODO

- **Severity:** P3 (future-risk; works today)
- **Page / file:** `apps/transcribe-md/src/components/ui/top-nav.tsx:52-64`
- **What it is:** The Cmd-K button synthesises a `KeyboardEvent` and
  dispatches it on `document` to open the global command palette. The
  inline TODO admits this is a hack: "replace with a direct store
  opener once the palette is re-wired."
- **Why P3:** If a future refactor switches the `<CommandPalette>`
  keyboard hook from document-listener to React-state, the synthesised
  event becomes orphan and the palette button silently no-ops. Pattern
  A risk, latent.
- **Recommended fix scope:** small (replace synthesised event with a
  shared store call), but tied to whatever palette refactor lands.
- **Walker observability:** `sweep-dashboard.mjs` will catch this if
  the palette ever stops opening — the click classification flips from
  `VISUAL_ONLY` to `NO_NETWORK_FIRED`.

### Finding F-14 — Orphan `<PatientTabs>` component

- **Severity:** P3 (dead code)
- **File:** `apps/transcribe-md/src/app/patients/[id]/patient-tabs.tsx`
- **What it is:** Exports `<PatientTabs>` with `active` + `trash` keys
  but nothing imports it. The page itself renders an inline `<TabBar>`
  with the full 4-tab set. The header doc-comment admits "Currently
  unused."
- **Recommended fix scope:** delete the file or document why it's
  retained. Same shape as PR #134's `SOAP_JUMP_EVENT` cleanup.

### Finding F-15 — `void logAudit()` racy on slow VPS

- **Severity:** P3 (test-flake, not a product bug)
- **File:** `apps/transcribe-md/src/app/patients/[id]/page.tsx:170`
- **What it is:** `void logAudit({ action: 'VIEWED_PATIENT_FILE', ... })`
  fires fire-and-forget. On slow VPS, the RSC render can complete
  (and the walker can move on) before the audit row hits postgres.
  `auditDelta` becomes flaky.
- **Recommended fix scope:** none today. Walker should bump its
  settle window from 800 ms to 1200 ms when running on this VPS, OR
  the page action should `await logAudit()` (small perf cost).

### Finding F-16 — Filter-pill locator collision-prone

- **Severity:** P3 (walker hardening)
- **File:** `apps/transcribe-md/src/app/visits/page.tsx` filter-bar
  component
- **What it is:** The walker matches each filter pill by visible
  text ("All" / "Ready" / etc). If a future copy change introduces
  another "All" elsewhere on the page (e.g. an aria-label), the
  walker's locator collapses on the wrong element.
- **Recommended fix scope:** add `data-testid="filter-pill-{id}"` to
  each pill in the JSX. Walker switches to `getByTestId()`.
