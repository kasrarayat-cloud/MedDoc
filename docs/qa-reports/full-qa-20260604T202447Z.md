## How it was run (isolation)
The repo ships **no isolated test DB** — the E2E/seed/cleanup harness is hardwired to the prod `meddoc` DB with only `qa-e2e-` email-prefix scoping (see F1). So I stood up a parallel, fully-isolated stack:
- `docker-compose.qa.yml`, project `meddoc-qa`: own `postgres`/`redis`/`minio` (fresh named volumes, never the prod `/mnt/pgdata-encrypted` mount), app on `127.0.0.1:9020`, worker — all from the **already-built prod images** (no rebuild → no heap-OOM risk).
- `MOCK_AI_CALLS=true` + **dummy** `ANTHROPIC_API_KEY`/`DEEPGRAM_API_KEY` → the stack physically cannot reach real APIs or burn tokens.
- Schema via the cached `meddoc-pro-db-migrate` image (`prisma migrate deploy`) against the qa DB only.
- Verified isolation at every mutating step: qa empty→migrated, prod md5 re-checked unchanged after migrate / E2E / UI walk / teardown.
- Auth: `EMAIL_AUTO_CONFIRM_DOMAINS=test.dev` + `EMAIL_AUTO_CONFIRM_ALLOW_IN_PROD=true` + a throwaway `AUTH_SECRET`.

Browser: bundled chromium (`chromium-1217`) via Playwright directly — never the MCP/chrome-channel. The prod-defaulting `qa-interaction-auditor` walkers were **not** used (they default to `https://app.quillmd.com` + prod containers across 30+ files — too leak-prone on a PHI box); I wrote a `:9020`-hardcoded walker instead.

## Findings (all surfaced for triage — none inline-fixed)

### F1 — [P1 · process/safety] E2E/seed/cleanup harness is hardwired to the PROD database
The only documented way to run the E2E suite runs it against the **live prod stack/DB** (`tests/e2e/README.md`; `cleanup.ts` → `docker compose -f /opt/meddoc-pro/docker-compose.yml exec postgres psql -U meddoc -d meddoc`), isolated only by `qa-e2e-` email prefix. An aggressive sweep (or the note-format **activate**, which transactionally supersedes a doctor's active template) would mutate real PHI/doctor state.
**Recommendation:** add a fail-closed guard to seed/cleanup (refuse unless `DATABASE_URL` host ≠ prod) and parameterize `cleanup.ts`'s compose target; document the isolated-stack pattern used here.

### F2 — [P2 · test-debt] E2E scenario suite (1–4) is stale → regression suite is RED
All 4 scenarios `goto('/visits/new')` then immediately click a mode tile (`/upload audio/`, `/dictate live/`, `/text to soap/`). But `/visits/new` is now a **two-step flow** — step 1 is the patient-picker (`patient-picker.tsx`), the mode tiles live in step 2 (`visit-form-step2.tsx`). The specs skip step 1 → `locator.click` timeout. Signup itself works (the scenarios create verified users first). **Net: the visit→SOAP→sign path is unguarded by the suite.**
**Repro:** `npm run test:e2e` (chromium) → scenarios 1–4 fail waiting for the mode-tile button on `/visits/new`.
**Recommendation:** update the 4 scenarios to create/select a patient (step 1) before clicking the mode tile. (Substantive test-logic change — not inline-fixed to avoid masking a real issue.)

### F3 — [P3 · test-debt] mobile-tap-targets probes a non-existent `/settings/security`
`mobile-tap-targets.spec.ts:160` asserts `/settings/security` returns 2xx/3xx, but only `/settings/security/mfa` has a page and **nothing links to `/settings/security`** → 404 → test fails. Not a user-facing broken link.
**Recommendation (decision needed):** point the test at `/settings/security/mfa`, OR add a `/settings/security` landing page if one was intended.

### F4 — [P3 · test-infra, qa-only] E2E cleanup command errored under the qa-compose override
Under my `E2E_CLEANUP_COMPOSE` override, `cleanup.ts`'s multi-line `psql` via `docker compose -f docker-compose.qa.yml exec -T` failed (SQL-escaping/exec quirk), leaving qa-e2e users in the qa DB (irrelevant — qa volume was destroyed). **Prod cleanup works** (prod `qa-e2e-%` count = 0). No prod impact; noting for completeness.

### F5 — [P3 · data hygiene] Prod holds residual test accounts
Prod has **7 `@test.dev` + 1 `@quillmd.test`** user accounts (the latter is the seeded `qa-auditor@quillmd.test`). None are `qa-e2e-`prefixed, so the E2E cleanup never targets them. (The 301 "Solo —" practices are normal real-doctor signups.)
**Recommendation:** confirm these are intentional seeded accounts or purge them; consider a periodic non-prefix test-account audit.

### F6 — [P3 · observability] Worker heartbeat probe reports "healthy" during a fatal boot crash
When the worker was missing `AUTH_SECRET`, it threw on boot yet the container reported **healthy** (the heartbeat liveness probe only checks `/tmp/worker-heartbeat` freshness, which was still being written). A misconfigured worker can look healthy. (Encountered in the qa env; prod gets `AUTH_SECRET` from `.env`, so prod is unaffected — but the probe gap is real.)
**Recommendation:** gate the heartbeat on successful boot (queue-connected) rather than process-alive.

### F7 — [observation · test coverage gap] Note-format AI flow can't run under MOCK
`tm_template_parse` + `tm_template_phi_scan` have **no `MOCK_AI_CALLS` fixtures** (`packages/ai/src/mock.ts`), so under mock the note-format parse throws (and SOAP generation returns a fixed 4-header note regardless of template). The note-format upload→parse→activate→generate flow therefore isn't E2E-testable without real AI. (Real generation under the Dr. A template was separately proven end-to-end in the prior task.)
**Recommendation:** add mock fixtures for `tm_template_parse` + `tm_template_phi_scan` so the note-format flow is coverable in CI.
