### Flag #1 — SIGNED state UI is not visually distinct from READY

**Where:** `/visits/<id>` when `signedAt IS NOT NULL` and `status = READY`.

**Observed:** Both states render identical chrome — same status pill ("Ready"), same "Sign & Send" CTA visible bottom-right, same SOAP body card layout, same breadcrumb (`Visit · ready`). The only difference visible in the screenshots is the SOAP body content, which comes from data, not from the UI distinguishing the state.

**On the visits list:** The same gap repeats — the third visit in the seeded set (status=READY, signedAt=NOW) shows a "Ready" pill identical to the unsigned READY visit, not a "Signed" pill or distinct dot color. The list page even has a "Signed" filter pill in its filter row (so the design intent exists), but the per-row badge doesn't reflect signedAt.

**Why it matters:** A doctor who already signed a note may be invited to sign it again from the visit detail; on the list view they cannot tell at a glance which notes are still pending vs already finalized.

**User judgment needed:** Is this a known scope deferred to a post-merge follow-up, or a regression to fix before merge? If it was already flagged in `qa-remodel` Phase 2 (the `🟡 PASS-WITH-FLAGS` verdict from `6aada04`), it may already be on the post-merge backlog.

## ⚪ Harness-side skips (not code defects)

### Skip #1 — `/admin` returned 404

**Cause:** The runner promotes the test user to `SUPER_ADMIN` via direct SQL UPDATE, but the storage-state cookie was issued at signup with `role=DOCTOR` embedded in the JWT. Middleware checks the JWT (not the DB on every request), so the role-stale JWT routes /admin to a 404 by the deny-by-existence pattern.

**Production impact:** None — real users get a fresh JWT at login that reflects their current role. This only affects the merge-prep harness.

**Mitigation in this run:** Did not visually verify /admin. The skill v1.0.0 documents two viable fixes for next iteration: (a) re-login after promotion to refresh the JWT, or (b) issue a new session via NextAuth's session-callback hook. v1.1.0 of the skill should pick one.

### Skip #2 — `/dev/rx-warnings?variant=critical` returned 404

**Cause:** The route is gated on `process.env.NODE_ENV === 'development'`. Stage 3 builds in production mode, which excludes the route from the route table.

**Production impact:** None — /dev/* routes are intentionally never live in production. The Rx-warning visual reference is for engineering review only.

**Mitigation in this run:** Skill design Option A (parallel `next dev -p 8767`) was not exercised because Option B (skip) was sufficient for this gate. Future merge-prep runs that need to verify Rx-warning card rendering can add an opt-in flag to spawn the dev instance.
