## P0 findings

### Finding F-01 — EM_OVERRIDE_EVENT dispatched, no listener — doctor's E&M code override silently discarded

- **Severity:** P0
- **Pattern:** A (orphan dispatcher)
- **Page / workflow:** `/visits/{id}` visit-ready view → Coding Rail → "Override" dropdown
- **Element:** E&M code option (e.g. "99214") in the override dropdown
  (`apps/transcribe-md/src/components/visits/CodingRail.tsx:362`)
- **What the user sees:**
  - Doctor opens the Coding Rail override dropdown.
  - Picks a different E&M code (e.g. overrides the AI's `99213` to `99214`).
  - Toast appears: **"Override set to 99214 — Doctor-set code recorded in audit trail."**
  - Modal closes; rail re-renders with the new code displayed.
- **What actually happens:**
  - `handleOverrideSelect` at `CodingRail.tsx:221-233` builds an
    `EmOverrideDetail` payload and calls
    `window.dispatchEvent(new CustomEvent(EM_OVERRIDE_EVENT, { detail }))`.
  - `grep -rEn "addEventListener\(EM_OVERRIDE_EVENT" apps/transcribe-md/src/`
    returns ZERO matches.
  - No PATCH request fires. `transcribe_visits.cptCodes` is unchanged.
  - **No `audit_logs` row is written** — the toast text is a lie.
  - When the doctor reloads the page, the override is gone (the rail
    re-derives from server-state, which never received the override).
- **Evidence (from static analysis):**
  - Dispatcher: `CodingRail.tsx:226` —
    `window.dispatchEvent(new CustomEvent(EM_OVERRIDE_EVENT, { detail }));`
  - Constant declaration: `lib/em-coding-ui/types.ts:169` —
    `export const EM_OVERRIDE_EVENT = 'qm:em-override';` with comment
    "Fired by the override dropdown — **backend wiring belongs to Subagent B.**"
  - Adjacent comment at `CodingRail.tsx:227` confirms the deferral:
    "Optimistic local toast — **Subagent B wires the actual PATCH endpoint.**"
  - PASS B (DB diff + Caddy mutation log) was skipped, but the
    static-analysis evidence is sufficient: the dispatched event has
    no listener anywhere in the tree, and there is no PATCH endpoint
    at `apps/transcribe-md/src/app/api/visits/[id]/em-score/override*`.
- **Why the user action is what it is:**
  - **User action:** doctor reviewing the AI's E&M tier and disagreeing
    (the override dropdown is the explicit "I, the human, override the
    AI's coding decision" affordance — most-touched in coding-coach
    review traffic).
  - **Intent:** PATCH `/api/visits/{id}/em-score/override` →
    update `transcribe_visits.cptCodes` to the doctor's chosen tier →
    write `audit_logs` row (action `EM_CODE_OVERRIDDEN` or similar)
    → return updated EmScore so the rail re-renders authoritatively.
  - **What's silently broken:** every override since this code shipped
    has been thrown away. Billing reflects the AI's tier; HIPAA audit
    trail has no record the doctor ever overrode anything.
- **Recommended fix scope:** **medium** (per memory #18).
  - Server: add `POST /api/visits/[id]/em-score/override` that updates
    `cptCodes`, writes audit row, returns refreshed EmScore. Mirror the
    shape of the apply-additions endpoint that PR #132 already shipped.
  - Client: replace the dispatch at `CodingRail.tsx:226` with a prop
    callback `onApplyOverride?: (code: EmCode, reason?: string) =>
    Promise<{ ok: boolean; error?: string }>` and wire it from
    `soap-editor.tsx` (same pattern PR #132 used for `onApplyAdditions`).
  - Schema: add `EM_CODE_OVERRIDDEN` to the `AuditAction` enum (mirror
    of `EM_BUMP_APPLIED` from PR #132's migration
    `20260505220000_em_bump_applied_audit_action`).
- **Escalate to:** none — fix inline. The fix is a direct mirror of
  the PR #132 stub-completion pattern; no specialist-agent diagnosis
  needed. (If the doctor-override use-case implies a billing-correctness
  policy decision — e.g. capping how high a doctor can up-code — that's
  a Kasra/clinical-leadership call, not a specialist-agent triage.)
- **Reproduction (post-test-user-seed):**
  ```
  # 1. As the test user, create a visit + run the pipeline to READY
  # 2. Open /visits/{id}
  # 3. Click the Coding Rail override dropdown
  # 4. Click any non-default code option
  # 5. Observe the success toast
  # 6. Verify nothing changed:
  docker exec meddoc-pro-postgres-1 psql -U meddoc -d meddoc -tA -c \
    "SELECT \"cptCodes\", \"updatedAt\" FROM transcribe_visits WHERE id = '<vid>';"
  docker exec meddoc-pro-postgres-1 psql -U meddoc -d meddoc -tA -c \
    "SELECT action, \"createdAt\" FROM audit_logs WHERE \"targetId\" = '<vid>' ORDER BY \"createdAt\" DESC LIMIT 5;"
  # cptCodes unchanged + no EM_CODE_OVERRIDDEN row = bug confirmed
  ```

### Finding F-02 — SOAP_HIGHLIGHT_CRITERIA_EVENT dispatched, no listener — bump CTA can't tell doctor where to fill in

- **Severity:** P1
- **Pattern:** A (orphan dispatcher)
- **Page / workflow:** `/visits/{id}` visit-ready view → Coding Rail → "Bump to 99214 → +$32" CTA
- **Element:** Bump CTA button
  (`apps/transcribe-md/src/components/visits/BumpCtaButton.tsx:74-92`)
- **What the user sees:**
  - Doctor sees the sage "Bump to 99214 · +$32 · close 2 gaps" CTA.
  - Clicks it.
  - BumpModal opens (the `onClick` prop wires correctly to
    `handleBumpClick` in `CodingRail.tsx:238-240`).
  - SOAP body **does NOT** highlight the gap criteria, **does NOT**
    auto-scroll, **does NOT** show the sage edge-glow that the design
    promises.
- **What actually happens:**
  - `BumpCtaButton.tsx:60-62` dispatches
    `new CustomEvent(SOAP_HIGHLIGHT_CRITERIA_EVENT, { detail })` with
    the gap criterion ids.
  - `grep -rEn "addEventListener\(SOAP_HIGHLIGHT_CRITERIA_EVENT" apps/transcribe-md/src/`
    returns ZERO matches.
  - The event fires into the void; SOAP body never sees it.
  - `onClick()` (the modal-open callback) still works, so the doctor
    can read the criteria in the modal copy. Workflow recoverable.
- **Evidence:**
  - Dispatcher: `BumpCtaButton.tsx:60-62`.
  - Constant: `lib/em-coding-ui/types.ts:160` —
    `export const SOAP_HIGHLIGHT_CRITERIA_EVENT = 'qm:soap-highlight-criteria';`
    with comment "Fired by the rail when the doctor accepts a bump
    → SOAP body highlights gap criteria."
  - Inline comment at `BumpCtaButton.tsx:14-16`: "ALSO emits
    `qm:soap-highlight-criteria` so **Subagent A's body applies the
    sage edge-glow + auto-scrolls to the first missing criterion.**
    Loose coupling — no shared store."
- **Why the user action is what it is:**
  - **User action:** doctor sees "+$32 if you close 2 gaps" → wants to
    know WHERE in the SOAP to add what to claim the higher tier.
  - **Intent:** SOAP body should pulse / outline the relevant section
    (e.g. ROS row if `ros` is the missing criterion) and auto-scroll
    to it. Doctor sees the visual cue, edits inline, re-clicks Bump.
  - **What's degraded:** the doctor must read the BumpModal copy to
    figure out which gaps to fill; the SOAP body itself is silent.
    Slower workflow, higher friction; but the data path (apply
    additions via PR #132's `onApplyAdditions`) still works.
- **Recommended fix scope:** **small-medium**.
  - Add a listener in `soap-editor.tsx` (or a `SoapHighlightHost`
    component) that receives the criterion ids, mutates section
    refs to add a `qm-soap-section--highlight` class for ~3s, and
    scrolls the first hit into view. Pure client-side; no server work.
  - Optional: extend `SoapHighlightCriteriaDetail.scrollTo` (already
    in the interface at `types.ts:165`) so the dispatcher passes the
    target section explicitly.
- **Escalate to:** none — fix inline.

### Finding F-03 — SOAP_EDITED_EVENT listener present, no dispatcher — rail's debounce-rescore never fires after SOAP edits

- **Severity:** P1
- **Pattern:** A inverse (orphan listener — feature exists but never driven)
- **Page / workflow:** `/visits/{id}` visit-ready view → SOAP body → inline edit
- **Element:** SOAP section inline edit fields
  (`apps/transcribe-md/src/app/visits/[id]/soap/SoapInlineEdit.tsx` — the doctor's
  primary edit affordance) — they don't dispatch even though something has to.
- **What the user sees:**
  - Doctor types into a SOAP section (inline edit).
  - Server-side draft save fires (debounced) — that part works.
  - The Coding Rail's E&M score should re-compute as the doctor types
    so the tier badge updates live.
  - **Tier badge never updates while the doctor is typing.** Only a
    full page reload re-fetches the score.
- **What actually happens:**
  - `CodingRail.tsx:182-211` registers a listener:
    `window.addEventListener(SOAP_EDITED_EVENT, handler);`
  - The handler debounces by `RESCORE_DEBOUNCE_MS` then calls
    `rescore(text)` to update the rail with a fresh tier.
  - `grep -rEn "dispatchEvent\(.*SOAP_EDITED_EVENT" apps/transcribe-md/src/` and
    `grep -rEn "'qm:soap-edited'" apps/transcribe-md/src/` both
    return ZERO matches at any dispatch site (only the listener +
    cleanup + import).
  - `BumpModal.tsx:21` describes the contract — "the modal mutates
    the SOAP body the parent rail listens to (`qm:soap-edited`),
    triggering an immediate re-score" — but the modal's apply path
    in `CodingRail.tsx:242-258` doesn't dispatch the event either.
- **Evidence:**
  - Listener: `CodingRail.tsx:199, 201`.
  - Constant: `types.ts:152` — declared + interface defined.
  - Documented contract: `BumpModal.tsx:21`, `types.ts:151`.
  - Confirmed orphan: full repo grep returns 0 dispatchers.
- **Why the user action is what it is:**
  - **User action:** doctor edits SOAP inline → expects the E&M tier
    badge to refresh as they type so they can see whether their edits
    have crossed the bump threshold.
  - **Intent:** the SOAP body (or `SoapInlineEdit.tsx` save action)
    fires `qm:soap-edited` after each save → rail's debounce handler
    rescores client-side → badge updates without a reload.
  - **What's degraded:** the rail badge is stale during editing. When
    the doctor accepts a bump via modal, the rail is supposed to
    rescore optimistically — but since no dispatcher fires, it doesn't.
    Workflow still works (data is correct after reload) but the live
    feedback loop is broken.
- **Recommended fix scope:** **small**.
  - Add a single `window.dispatchEvent(new CustomEvent(SOAP_EDITED_EVENT, {
    detail: { visitId, soapText } }))` call in the SOAP save path
    (probably `SoapInlineEdit.tsx` after the debounced save) and in
    `CodingRail.tsx:258+` after `onApplyAdditions` resolves.
  - One-line dispatch in two places. No new state, no new components.
- **Escalate to:** none — fix inline.

### Finding F-04 — qm:em-boost-hints listener present, no dispatcher — SOAP-section pulse dots never surface

- **Severity:** P1
- **Pattern:** A inverse (orphan listener)
- **Page / workflow:** `/visits/{id}` visit-ready view → SOAP body section heads
- **Element:** `SoapSection` heading components — they're set up to
  show sage/amber pulse dots when the rail flags them as gating a
  higher E&M tier, but the rail never sends the signal.
- **What the user sees:**
  - Doctor sees the SOAP body with no visual indication of which
    sections are blocking a tier bump.
  - Designed-but-absent pulse dots: the soap-v6 mockup pulses sage
    on Subjective when `ros` is missing, amber on Plan when MDM
    elements gate `99214`, etc. Currently — nothing.
- **What actually happens:**
  - `soap-editor.tsx:128-135` registers a listener for
    `'qm:em-boost-hints'` and stores the payload in `boostHints`
    state, which propagates into section heads.
  - `grep -rEn "qm:em-boost-hints" apps/transcribe-md/src/` returns
    ZERO dispatchers — only the listener + cleanup at lines 132/133
    and the explanatory comment at line 120.
- **Evidence:**
  - Listener + state mirror: `soap-editor.tsx:124-135`.
  - Comment at `soap-editor.tsx:119-122`: "**Phase 5.2 — boost hints
    are surfaced by the CodingRail via the `qm:em-boost-hints`
    CustomEvent** (loose coupling, no shared store). The body
    listens and re-renders with sage/amber pulse dots in the section
    heads when the rail flags a section as gating a higher tier."
  - The CodingRail computes `sectionPulseHints` (`types.ts:142`) but
    never dispatches it to the body.
  - **Note:** unlike SOAP_EDITED/SOAP_HIGHLIGHT_CRITERIA, this event
    isn't a declared constant — it's a bare string literal
    (`'qm:em-boost-hints'`). Dispatcher would need to use the same
    bare-string form OR a new `EM_BOOST_HINTS_EVENT` constant.
- **Why the user action is what it is:**
  - **User action:** doctor scans the SOAP looking for what to
    flesh out to bump the tier.
  - **Intent:** rail computes which sections gate the tier bump →
    dispatches `qm:em-boost-hints` with `{ subjective: 'sage', plan:
    'amber' }` → body shows the dots → doctor's eye is drawn to the
    right place.
  - **What's degraded:** the doctor has no visual cue at the section
    level. They see the bump CTA copy ("close 2 gaps · 30 sec") and
    the modal's per-criterion suggestions, but the SOAP itself stays
    quiet about where the gaps live.
- **Recommended fix scope:** **small**.
  - Dispatch `'qm:em-boost-hints'` from `CodingRail.tsx` whenever
    `score.sectionPulseHints` updates — a `useEffect` on
    `[score.sectionPulseHints]` that fires the event with the hints
    object as `detail`. ~5 LOC.
  - Optional: promote the bare string to an `EM_BOOST_HINTS_EVENT`
    constant in `types.ts` for consistency.
- **Escalate to:** none — fix inline.
