## P1 findings

### Finding F-07 — `seed-qa-user.ts` doesn't set `emailVerified`; login refuses

- **Severity:** P1 (blocks PASS B by default; one-line fix)
- **Pattern:** Fixture gap (not a product bug)
- **Page / workflow:** `/login` — server action `signInAction`
- **Element:** "Sign in" button at `app.quillmd.com/login`
- **What the user sees:**
  - Doctor (or QA agent) submits the credentials seeded by
    `seed-qa-user.ts`.
  - Login form posts to `/login` (HTTP 200).
  - URL stays at `/login`.
  - Form-level error: **"Please verify your email before signing in.
    We sent a verification l[ink]…"**
  - PASS B aborts at the login step.
- **What actually happens:**
  - `users.emailVerified` is NULL on the seeded row because
    `seed-qa-user.ts` doesn't pass it through to `prisma.user.upsert`.
  - The login flow gates on `emailVerified !== null` and refuses.
  - Manual fix: `UPDATE users SET "emailVerified" = NOW() WHERE email
    = 'qa-auditor@quillmd.test';` — the QA agent ran this once + the
    walk proceeded.
- **Evidence:**
  - `apps/transcribe-md/scripts/seed-qa-user.ts:97-122` — the upsert
    `update`/`create` blocks set role / isActive / lockedUntil /
    failedLoginCount / practiceId / specialty / timeZone but **omit
    `emailVerified`**.
  - Reproduction (agent's own diagnostic):
    ```
    docker exec ... psql ... -c "SELECT \"emailVerified\" FROM users
        WHERE email = 'qa-auditor@quillmd.test';"
    ```
    returns null on a fresh seed; login rejects until UPDATE.
- **Recommended fix scope:** **trivial** (one-line patch).
  - Add `emailVerified: new Date()` to both the `update` block and the
    `create` block of the `prisma.user.upsert` call. Pre-verify the
    seeded test account so the QA agent never has to hand-bypass the
    verification gate.
- **Escalate to:** none — fix inline.

### Finding F-08 — `seed-qa-user.ts` doesn't grant `Product.TRANSCRIBE_MD`; login routes to wrong app

- **Severity:** P1 (blocks PASS B even after F-07 fix; one-line fix)
- **Pattern:** Fixture gap
- **Page / workflow:** `/login` — server action `signInAction` →
  `apps/transcribe-md/src/actions/auth.ts:213-230` cross-app gate
- **Element:** "Sign in" button at `app.quillmd.com/login` (after F-07
  manually fixed)
- **What the user sees:**
  - Login form submits.
  - URL stays at `/login`.
  - Form-level error: **"This account is for MedDoc Pro, not
    TranscribeMD. Continue to the right app:"** with a "Go to MedDoc
    Pro" CTA.
- **What actually happens:**
  - `users.products` defaults to `['MEDDOC_PRO']` per the schema:
    `products Product[] @default([MEDDOC_PRO])` (`packages/db/prisma/
    schema.prisma`).
  - The seed script doesn't set `products`, so the QA test user has
    `[MEDDOC_PRO]`.
  - The transcribe-md auth flow detects the missing `TRANSCRIBE_MD`
    entitlement and redirects to the MedDoc Pro app
    (`apps/transcribe-md/src/actions/auth.ts:213`).
  - Manual fix: `UPDATE users SET products = ARRAY['TRANSCRIBE_MD']::
    "Product"[] WHERE email = 'qa-auditor@quillmd.test';` — agent
    ran this once + the walk proceeded.
- **Evidence:**
  - `apps/transcribe-md/scripts/seed-qa-user.ts` — upsert blocks omit
    `products`.
  - `apps/transcribe-md/src/actions/auth.ts:213-230` — the cross-app
    redirect message + URL.
  - SQL verification:
    ```
    docker exec ... psql ... -c "SELECT products FROM users WHERE
        email = 'qa-auditor@quillmd.test';"
    ```
    returns `{MEDDOC_PRO}` after seed; UPDATE to `{TRANSCRIBE_MD}`
    unblocks login.
- **Recommended fix scope:** **trivial** (one-line patch).
  - Add `products: [Product.TRANSCRIBE_MD]` to both the `update` and
    `create` blocks. Either import `Product` from `@prisma/client` or
    use the string literal `['TRANSCRIBE_MD']` (the schema enum lives
    in Prisma's runtime).
- **Escalate to:** none — fix inline.

**Combined fix sketch for F-07 + F-08** (one PR, ~6 LOC total):

```ts
// apps/transcribe-md/scripts/seed-qa-user.ts
const user = await prisma.user.upsert({
  where: { email: QA_EMAIL },
  update: {
    passwordHash,
    role: 'DOCTOR',
    isActive: true,
    lockedUntil: null,
    failedLoginCount: 0,
    emailVerified: new Date(),         // ← F-07 fix
    products: ['TRANSCRIBE_MD'],       // ← F-08 fix
    practiceId: PRACTICE_ID,
    specialty: 'family-medicine',
    timeZone: 'America/Los_Angeles',
  },
  create: {
    email: QA_EMAIL,
    name: 'QA Interaction Auditor',
    passwordHash,
    role: 'DOCTOR',
    isActive: true,
    emailVerified: new Date(),         // ← F-07 fix
    products: ['TRANSCRIBE_MD'],       // ← F-08 fix
    practiceId: PRACTICE_ID,
    specialty: 'family-medicine',
    timeZone: 'America/Los_Angeles',
  },
});
```

The two findings cluster into a single seed-script patch.

### F-Bonus-01 — fixture SOAP didn't trigger bump CTA

- **Bonus:** true; Severity: P3 (fixture)
- The synthetic SOAP I inserted (122 chars) was short enough that the
  L7b CPT scorer produced `bumpableTo: null`. So the bump CTA never
  rendered, and the bump-flow + section-pulse-hint paths were not
  exercised on this walk.

  HPI/Exam/MDM content so the engine produces a 99213 → 99214 bump
  suggestion. Then the agent can verify:
  - Bump CTA renders.
  - Click → `onHighlightCriteria(criterionIds)` fires.
  - Sage edge-glow class lands on Subjective + Plan sections per the
    F-02 fix.
  - Bump modal opens with editable additions.
  - Apply & save → 200 + `EM_BUMP_APPLIED` audit row + score advance.

### F-Bonus-02 — fixture Rx warnings lacked `severity: "critical"`

- **Bonus:** true; Severity: P3 (fixture)
- The agent's fixture used `severity: "minor"` and `severity:
  "major"` only. The Rx-warning override button + sign-block flow is
  gated on `severity === "critical"` (per `rx-tab.tsx:445`). With no
  critical-severity warnings the override button never rendered + the
  sign action never blocked, so the Rx-override audit chain
  (`RX_OVERRIDE_RECORDED` + `RX_SIGN_BLOCKED_NO_OVERRIDE`) was not
  exercised.
- Recommended for next run: add a `severity: "critical"` warning to
  the fixture (e.g. drug-drug interaction with the patient's
  warfarin) so the override interaction is exercised.

### F-Bonus-03 — Transcript tab not rendered in text-notes mode

- **Bonus:** true; Severity: P3 (expected behaviour, NOT a bug)
- The Transcript tab is only present when the visit has utterances
  (audio_upload / voice_dictation modes). Our text-notes fixture
  produced no utterances, so the tab was correctly absent.
- The agent's tab-navigation matrix should branch on `inputMode` to
  avoid surfacing this as a "missing element" finding in future
  reports.
