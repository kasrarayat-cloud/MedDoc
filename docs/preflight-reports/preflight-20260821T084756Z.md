## ⚠️ THE CHECK-2 AUTO-FIX WAS DECLINED, DELIBERATELY

The skill's trigger fired — images reclaimable **53.87GB > 5GB** — and the
prescribed fix is `docker image prune -af --filter "until=168h"`.

**It was not run, and this is a judgement worth recording rather than a
skipped step.** `prune -a` removes any image no CONTAINER references, and
that includes **TAGGED** ones. This host holds **146 rollback-tagged images**
(`meddoc-pro-transcribe-md:pre-<sha>-<date>` and its worker twin) — the
documented rollback path for every past deploy, including the ones
`DEPLOYMENT_RUNBOOK.md §3.1–3.2` names by tag. Everything older than seven
days would have gone.

The safety rules already forbid auto-pruning **volumes** because they hold
data. A rollback tag is the same class of thing one layer up: it is the only
artifact that makes a bad deploy reversible, and it cannot be rebuilt from
`main` once the tree has moved.

**Nothing is blocked by declining it.** Disk is at 70% with 86G free — ample
for an image build — so the prune buys nothing this deploy needs and risks
something it may need badly. Build Cache is 39.16GB with **0B reclaimable**,
so the other trigger has nothing to collect either.

**Filed for a human decision:** a retention policy for rollback tags (keep the
last N, or the last N days, and prune older ones BY NAME) would let this
reclaim run safely. Until that exists, this auto-fix stays declined here.
