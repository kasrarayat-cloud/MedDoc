## ⚠️ Check 2 — the auto-fix rule is unsafe on this host, and was NOT executed

The skill says: *Images reclaimable > 5 GB → `docker image prune -af --filter "until=168h"`*.
Reclaimable is **116.7 GB**, so the rule fires. It was **not** run.

`docker image prune -a` removes every image not referenced by a **running
container**. On this host that set includes the entire documented rollback tag
table:

```
meddoc-pro-transcribe-md:pre-exportguard-20260728        (2 days)
meddoc-pro-transcribe-md:pre-emrehome-20260728           (2 days)
meddoc-pro-transcribe-md:pre-readonlypaper-20260728      (2 days)
meddoc-pro-transcribe-md:pre-lanedelete-20260727         (2 days)
meddoc-pro-transcribe-md:pre-auditonly-20260727          (3 days)
meddoc-pro-transcribe-md-worker:pre-verifierfix-20260727 (4 days)
   … and each one's paired -worker image
```

`AGENTS.md` names `:pre-emrehome-20260728` as the **preferred rollback** for the
E/M surface, precisely because the flag rollback costs a capability and the image
rollback does not. `docs/DEPLOYMENT_RUNBOOK.md` §3.1–3.2 carries the full table.
The `until=168h` filter does not protect them — it *selects* them: every tag above
is older than 24h and all but one will cross 168h within the week. The filter
reads like a safety margin and is actually a countdown.

**Nothing was at risk here** — disk is at 70% with 86 G free and
`/var/lib/docker` is ~45% of the filesystem, well under the skill's own 60%
"stop and ask" line. There was no pressure to prune at all.

**Recommended change to the skill** (not made in this session — it is a shared
guardrail, not this task's scope): the Check 2 image rule must exclude the
rollback namespace, e.g. gate on `--filter "label!=..."` or an explicit
`grep -v ':pre-'` allowlist, and it should never fire while disk is under 80%.
An auto-fix whose blast radius includes the documented incident-recovery path
should not be reachable by an automatic verdict.
