## Check 2 — why the documented auto-fix was NOT run

The skill's rule is *Images reclaimable > 5 GB → `docker image prune -af --filter "until=168h"`*.
Reclaimable is 116.6 GB, so the trigger fires. **Running it on this host would
destroy the production rollback images.**

`docker image prune -a` removes every image not referenced by a *running*
container. A rollback tag is by definition not running — that is the entire point
of it. All of these are older than 168h or would become eligible, and all are
load-bearing:

```
meddoc-pro-transcribe-md:pre-emrehome-20260728          ← named in AGENTS.md as the
meddoc-pro-transcribe-md-worker:pre-emrehome-20260728     preferred E/M-surface rollback
meddoc-pro-transcribe-md:pre-readonlypaper-20260728
meddoc-pro-transcribe-md-worker:pre-readonlypaper-20260728
meddoc-pro-transcribe-md:pre-exportguard-20260728
meddoc-pro-transcribe-md-worker:pre-exportguard-20260728
meddoc-pro-transcribe-md:pre-auditonly-20260727
meddoc-pro-transcribe-md-worker:pre-auditonly-20260727
meddoc-pro-transcribe-md:pre-lanedelete-20260727
meddoc-pro-transcribe-md-worker:pre-lanedelete-20260727
meddoc-pro-transcribe-md-worker:pre-verifierfix-20260727
meddoc-pro-transcribe-md:rounds                         ← the flag-ON image the
                                                          rounds-board E2E pack builds on
```

`DEPLOYMENT_RUNBOOK.md` §3.1–3.2 keeps the tag table these belong to. Deleting
them converts a documented one-command rollback into a rebuild-from-source under
incident pressure.

**Not blocking:** disk is 70% with 87G free, so there is no pressure that would
justify the trade. 11 genuinely dangling images exist and could be cleared with
`docker image prune -f` (no `-a`), which is tag-safe — not run either, because
nothing needs the space today.

**Skill defect, for whoever maintains it:** the Check 2 auto-fix is unsafe as
written on any host that keeps tagged rollback images. It should filter to
dangling-only, or exclude `:pre-*`.
