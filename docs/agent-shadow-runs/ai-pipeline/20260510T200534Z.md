## Findings

### BLOCKING_REGRESSION · 1

#### `AI_PIPELINE_FINDING_001` — L3 / L7b / L7c high schema-validation failure rate

| Layer | Total calls | Failures | Error code | Failure rate |
|---|---|---|---|---|
| `tm_cpt_coding` (L7b) | 103 | 50 | 47× SCHEMA_FAIL, 3× JSON_PARSE_FAIL | **48.5%** |
| `tm_entities` (L3) | 68 | 15 | 15× SCHEMA_FAIL | 22.1% |
| `tm_icd_coding` (L7a) | 69 | 18 | 18× JSON_PARSE_FAIL | 26.1% |
| `tm_rx_drafting` (L7c) | 69 | 16 | 15× SCHEMA_FAIL, 1× JSON_PARSE_FAIL | 23.2% |

Overall pipeline failure rate across all `tm_*` purposes:
**120 / 718 = 16.7%**.

These are above the typical 5-10% retry tolerance most
production LLM pipelines target. The retry path in
`apps/transcribe-md/src/worker/lib/retry.ts` does cover schema
fails (so user-visible impact is limited per visit), but the
sustained failure rate inflates cost (`SCHEMA_FAIL` calls still
bill) and latency (each retry adds 10-30s).

**Likely root causes** (cross-referenced against the Phase 1
audit `findings/06-output-validation.md`):

- `tm_cpt_coding` SCHEMA_FAIL — Zod schema may have over-strict
  `.min(1)` validators on optional fields (per Q1 #19 / Q2
  §06.3 deferred in fix-pack 2).
- `tm_icd_coding` JSON_PARSE_FAIL — model output not consistently
  parseable; structured-output mode may not be wired (per Q1
  #19).
- `tm_rx_drafting` SCHEMA_FAIL — same shape; RxAction enum
  expansion (Q2 §06.7) already shipped, but other fields may
  still constrain too tightly.

**Severity:** BLOCKING_REGRESSION at the *agent* tier, advisory
at the *operator* tier (shadow). Worth escalating to a focused
"L3 / L7b / L7c schema-tightening" PR — partially overlaps with
`docs/ai-pipeline-fix-pack-2-status.md` deferred items.

### Advisory · 5

#### `AI_PIPELINE_FINDING_002` — `tm_transcribe` HTTP_400 + NETWORK_ERROR (9 / 58 = 15.5%)

Layer 1 (transcribe via Deepgram) has 9 failures: 6× HTTP_400,
2× NETWORK_ERROR, 1× generic `400`. The HTTP_400 cluster is
worth investigating — likely audio format / duration edge cases
that Whisper fallback handled (1 successful `whisper-1` call
recorded). Confidence-propagation work from Phase-1 audit §26.4
(PR #128) is live; this finding is the "what's left."

#### `AI_PIPELINE_FINDING_003` — `tm_soap_draft` 6× generic ERROR

L4 has 6 failures all marked `errorCode = 'ERROR'` (no specific
code). The retry-categoriser should be classifying these into
`HTTP_4XX` / `HTTP_5XX` / `TIMEOUT` / `SCHEMA` per the existing
taxonomy in `apps/transcribe-md/src/worker/error-categorize.ts`.
Generic `ERROR` suggests an unhandled error path.

#### `AI_PIPELINE_FINDING_004` — `transcribe_visits.transcriptionProvider` null on 58/64 visits

Only 6 visits record `deepgram-batch`; 58 have `transcriptionProvider`
NULL. Could mean (a) provider is being written inconsistently or
(b) the column was added after most existing visits processed
and was never backfilled. Either way the fallback-path audit
(Phase 4) can't compute primary-vs-fallback ratios reliably.

#### `AI_PIPELINE_FINDING_005` — `tm_template_fill` is undocumented in the agent's expected layer list

Only 3 calls in production, but the purpose is not in the AI Pipeline
Auditor's `data-sources.md` §1 expected layer list (L1 / L1b / L2 / L3 /
L4 / L5 / L6 / L7). New layer added without doc update — a soft
regression class flagged in `activation-criteria.md` "Pipeline shape
sanity" check.

#### `AI_PIPELINE_FINDING_006` — Specialty column has both canonical ids + legacy display names

Visit specialty distribution shows a mix:

| Specialty value | Count | Form |
|---|---|---|
| `Orthopedics` | 25 | Legacy display name |
| `Cardiology` | 20 | Legacy display name |
| `primary-care` | 10 | Canonical id |
| `Primary Care / Family Medicine` | 3 | Legacy display name |
| `Internal Medicine` | 2 | Legacy display name |
| `pain-management` | 2 | Canonical id |

`findSpecialty()` handles both via `LEGACY_TO_ID` fallback, so
runtime is correct, but reports / analytics / per-specialty
rollups will under-count canonical-id rows if a one-time
migration isn't run to normalize. Fix-pack 2 closed the
OB-GYN legacy-to-canonical mapping; the broader normalization
remains.
