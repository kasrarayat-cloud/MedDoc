## Findings · BLOCKING_TIER_1

### `HIPAA_FINDING_001` — §164.312(d) Zero MFA coverage on production accounts

**Phase:** 4 (Authentication)
**CFR cite:** §164.312(d) "Standard: Person or entity authentication"

```
                                role | mfa_on | total
--------------------------------------+--------+------
                              ADMIN   |   0    |   3
                              DOCTOR  |   0    |  43
                              STAFF   |   0    |   1
                       SUPER_ADMIN    |   0    |   2

Active accounts total: 49.  MFA enabled: 0 (0.0%).
```

Zero accounts have `mfaEnabled = true`, including the two
SUPER_ADMIN accounts. The `users` table has the MFA columns
provisioned (`mfaEnabled`, `mfaSecret`, `mfaVerifiedAt`,
`mfaBackupCodes`) and the audit-log enum includes MFA action
codes (`MFA_ENABLED`, `MFA_DISABLED`, `MFA_CHALLENGE_PASSED`,
`MFA_CHALLENGE_FAILED`) — but zero rows exist for any of those
actions. The MFA system is wired but not used.

**Why BLOCKING_TIER_1:** §164.312(d) requires "a person or
entity is the one claimed" — for a system handling PHI, MFA on
admin + clinical accounts is the de facto industry standard. A
counsel reviewer evaluating this would flag it as material.

**Operator action:** decide on the MFA rollout window
(soft-prompt → hard-required) before real-pilot users onboard.
At minimum, enable MFA for the two SUPER_ADMIN accounts today.

### `HIPAA_FINDING_005` — Audit action coverage analysis

**Phase:** 2 (Audit controls)

Of 99 `AuditAction` enum values, **43 have zero emissions to
date**. Most are *legitimately* zero (events that haven't
happened — `MFA_ENABLED`, `EXPORTED_AUDIT_LOG`, etc.). The
following are worth investigating because they SHOULD have fired
based on observed pipeline state:

| Action | Why expected to fire | Why zero matters |
|---|---|---|
| `TRANSCRIPTION_PROVIDER_FALLBACK` | 1 whisper-1 call recorded after 57 deepgram calls — implies a fallback happened | Either the fallback didn't actually invoke or the audit emit path is broken |
| `PIPELINE_REJECTED_INJECTION_DELIMITER` | Wired in fix-pack 2 (#191) on L2; zero attempts so far — could be positive | Positive signal IF no malicious content; verify the call path is reachable |
| `VISIT_RETRY_BUDGET_EXHAUSTED` | 120 ai_call failures recorded; the worker's retry policy must occasionally exhaust | Either retry never exhausts (positive — pipeline always succeeds eventually) OR the emit-on-exhaust path is broken |

**Not a blocking finding** — these need a runtime check (the QA
Interaction Auditor or operator manual verification). Flagged
here as data-source confidence.
