## Issue

A license sweep over `node_modules/` reveals **two non-permissive licenses** in the
dependency graph. Neither is GPL/AGPL/SSPL/BUSL (which would be deal-breakers for closed-
source SaaS), but both deserve documentation so an acquirer or a customer's IT/legal team
can answer "are you OK using this?" in five minutes instead of five hours.

## Risk

### `@sentry/cli` — FSL-1.1-MIT

Functional Source License v1.1 (Sentry's own license, applied to their CLI tool) is
**permissive for internal use** but restricts "Competing Use" — defined as building a
product that substitutes for Sentry. The license auto-converts to MIT after 2 years.

Relevant clauses (from `node_modules/@sentry/cli/LICENSE`):

> Permitted Purposes specifically include using the Software:
> 1. for your internal use and access;
> 2. for non-commercial education;
> 3. for non-commercial research; and
> 4. in connection with professional services...

We use `@sentry/cli` at **build time only** (it uploads source maps via
`@sentry/bundler-plugin-core`). We do not redistribute it; we do not build a Sentry
competitor. **Compliant — but undocumented.**

### `@img/sharp-libvips-*` — LGPL-3.0-or-later

`sharp` itself is Apache-2.0, but the bundled `libvips` binary is LGPL-3.0-or-later.
LGPL allows commercial use **as long as you can swap the LGPL'd library out** (i.e., dynamic
linking, OR redistribution of the object code in a form that allows relinking). For npm
packages this is satisfied automatically — `sharp` dlopens libvips, and any user can
`npm install sharp` against a different libvips. **Compliant by construction.**

The catch: if we ever ship a fully-static binary build (e.g., a `pkg`-bundled CLI), LGPL
compliance becomes non-trivial (need to ship the libvips object code or an offer to
provide). We don't currently do that.

### Other notable entries

- `jszip@3.10.1` — `(MIT OR GPL-3.0-or-later)`. The dual license means we operate under MIT;
  no risk.
- `@deepgram/sdk` — MIT (clean).
- `bullmq` — MIT (clean).
- `pdfkit` — MIT (clean).

## Recommended fix

1. Add a `docs/THIRD_PARTY_LICENSES.md` (or attribution NOTICE file) generated by
   `npx license-checker --production --workspaces --json` capturing the license of every
   production dep. Refresh in CI on every dep PR.

2. In the same doc, **explicitly call out** the two non-MIT entries:

   ```markdown
   ## Non-permissive licenses (vetted)

   ### @sentry/cli — FSL-1.1-MIT
   - Pulled transitively by @sentry/nextjs → @sentry/bundler-plugin-core
   - Used at build time only (source-map upload). Not redistributed.
   - Compliant with FSL "Permitted Purpose" #1 (internal use).
   - Auto-converts to MIT 2027-04-22 (2 years from 2.58.5 release).

   ### @img/sharp-libvips-* — LGPL-3.0-or-later
   - Native binary used by `sharp` (transitive of `next/image` for image optimisation).
   - Dynamically loaded via dlopen — LGPL permits commercial use under this model.
   - If we ever ship a static binary, we'd need to reassess.
   ```

3. Add a CI step that fails the PR if a *new* GPL/AGPL/SSPL/BUSL license appears in the dep
   graph. Quick approach:

   ```bash
   npx --yes license-checker --production --failOn 'GPL-2.0;GPL-3.0;AGPL-1.0;AGPL-3.0;SSPL-1.0;BUSL-1.1;CC-BY-NC-1.0;CC-BY-NC-2.0;CC-BY-NC-3.0;CC-BY-NC-4.0' \
     --excludePackages 'jszip@3.10.1'   # dual MIT-OR-GPL, we use MIT
   ```
