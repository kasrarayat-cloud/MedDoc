## WHY THIS DEPLOY — AND IT IS LIVE ON PRODUCTION TODAY

**Admin page data is readable UNAUTHENTICATED.** On `main`,
`app/admin/layout.tsx` is the only gate for every `/admin` page. Next 16 does
not re-run a layout on an RSC subtree refetch. A request carrying `RSC: 1` and a
`Next-Router-State-Tree` that marks `/admin` as already rendered therefore
renders the page alone: no cookie, no layout, and no audit row. `/api/admin/*`
is not affected, because each route is wrapped by `adminApi()`.

⚠️ **ON NEXT 16.3.4, WHICH PRODUCTION RUNS, THE HOLE SITS BEHIND ONE REDIRECT.**
The crafted request is first answered **307** to the same URL plus
`?_rsc=<hash>`. This is Next's cache-buster, and it is not a gate. A client
that follows it (every HTTP client can) reaches the page. So a probe that
stops at the 307 cannot tell a leaking build from a fixed one. Measured: the
unfixed and fixed builds return a byte-identical 307 and Location.

The earlier reproduction, on the QA stack's old 16.2.11 image, answered 200
directly.

**Measured on a QA build of the commit production runs (`b069ddbb`), following
the redirect:**
- `/admin/hipaa` returned 200 with **5 of 5** data markers;
- `/admin/threats` returned 200 with **2 of 2** data markers;
- both hosts gave the same result.

Production itself was **deliberately not probed** with the crafted request
before the fix.

**The fix** is `daaa379d`. `main` was merged in as `5d9e89ba`, and `5020c68a`
added tests and docs only. It is one request-cached verdict,
`readAdminVerdict()`, which requires `isActive`, the `SUPER_ADMIN` product,
`mfaEnabled` and a session under 12h. It is applied in three places:

- `requireAdminPage()` is the first statement of the layout and of every admin
  `page.tsx`.
- `assertSuperAdminCaller()` is the first statement of every exported async
  function under `app/admin/**/_lib`.
- `adminApi()` maps a helper refusal to its usual silent 404.

## THE ACT RUNS UNDER THE DISK WATCHDOG — FLOOR 6G, DECLARED HERE

The same wrapper as the composed deploy is used, armed until the first
production recreate (`=== 5b.`). It now also logs a free-disk sample every
poll, so the next deploy's budget is measured rather than estimated.

**The floor is 6G, not the earlier 8G, and the reason is arithmetic, not
convenience:**
- The composed deploy's build took free space from 34G to 14G, about 20G.
- About 28G is free now. That leaves about 8G at the expected peak, which is
  exactly the old floor.
- A kill before the first recreate is SAFE (production is untouched) but
  wastes the deploy. 6G still leaves room for postgres and minio writes across
  a build window of minutes.

If the build consumes more than about 22G, the watchdog kills it before any
recreate, and that is reported as a failed deploy, not as a pass.
