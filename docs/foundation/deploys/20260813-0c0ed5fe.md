## ⚠️ WHAT THIS DEPLOY CHANGES ABOUT BEHAVIOUR, STATED PLAINLY FIRST

A job whose failure is classified **permanent** is now **discarded** rather than
handed back to BullMQ for two more attempts it cannot benefit from. The log line
`permanent failure, fail-fast (skipping BullMQ retries)` has been false in
production since T-M23.A: it printed, and then the job retried anyway.

**Two consequences, and the second is the one this declaration exists to watch:**

1. A permanently-failed visit ends at `attemptsMade` **1 of 3** instead of 3 of 3.
2. **The DLQ must still receive it.** Session 01's own fix broke exactly this and
   caught it before merge — the `failed` handler dead-lettered on
   `attemptsMade >= opts.attempts`, which a discarded job never reaches, so every
   insufficient-balance refusal would have vanished from `/admin/queues`. The
   shipped predicate is `shouldDeadLetter`, written against *"this job will not
   run again"*. **Production cannot demonstrate either half tonight** — see the
   silent-deploy section below.

## ⚠️ PROVENANCE — THIS DECLARATION CANNOT BE COMMITTED BEFORE THE DEPLOY, AND THAT IS STRUCTURAL

Stated here rather than discovered in the transcript. `deploy-prod.sh` derives
the filename from `git rev-parse --short HEAD`, so a declaration for this deploy
**must** be named `20260813-0c0ed5fe.md` **and** HEAD must be `0c0ed5fe` when it
runs. Landing it through a PR first would move HEAD to that PR's merge commit and
the gate would then look for a different filename and refuse.

So the file is necessarily **uncommitted-on-`main`** at the moment of the deploy,
the gate reports `present` with its loud warning, and the ORDER is asserted by
the transcript rather than proved by git. **That is the sanctioned behaviour**
(ruling #96(b): strictness proportional to reversibility — a deploy is answerable
by a rollback) and it matches the `9d1a8b4e` deploy nine hours earlier.

⚠️ **But `RELAY.md`'s plan for this deploy — *"the declaration is necessarily its
own PR cycle, after this one merges and before the deploy session begins"* — does
not work, and this session is the one that found out.** Merging that PR is
exactly what invalidates the filename. Carried as a finding with a recommendation;
**not fixed tonight**, because widening the accepted filename is a weakening of a
shipped constraint and fails the provisional-ruling test.
