## What this deploy is, in one line

**Three new labels on a Postgres enum, plus an HTTP route that returns 503 to
every request because no webhook secret exists in production.** No Stripe
account, no key, no session-creation path. Nothing calls the top-up writer
because nothing can reach it.

### ⚠️ ASSERTION 7 IS THE FAIL-CLOSED ARM, AND 503 IS THE PASS

A 200 or a 400 here would mean `STRIPE_WEBHOOK_SECRET` is set in production —
which it must not be, because no Stripe account exists and the FOUNDATION
guardrail is TEST MODE ONLY. **503 is the route refusing before it reads the
body.** DISCOVERY §E.1 measured no `STRIPE` entry in any of the twelve `.env*`
files on disk; this assertion is what turns that measurement into a fact about
the running container.

⚠️ It is probed with **no `stripe-signature` header and an empty body**, which
is a request that can have no effect whatever the secret is. The route is
unauthenticated by design (§E.4), so probing it is not privileged access — it is
exactly what any internet caller can already do.

### ⚠️ ASSERTIONS 8 AND 17 ARE THE PAIR THAT MATTERS

B7 adds the **second** writer `ledger_entries` has ever had, and the first one
reachable from the public internet. Assertion 8 says no money moved. Assertion
17 says the route was not even *asked* to move any — because a
`CHECKOUT_TOPUP_REFUSED` row would mean a validly-signed Stripe event reached
production, which is impossible without a webhook secret and would therefore be
a finding about configuration, not about billing.

**A difference in either is THE FINDING**, whatever explanation is available
afterwards.

### `audit_logs` total is deliberately NOT pinned

It moves on ordinary traffic — a login, a page view. Pinning it would
manufacture a failure the deploy did not cause. Assertion 17 pins the slice this
deploy could possibly touch, which is the question actually being asked.

## Rollback

Tags cut **BEFORE** `deploy-prod.sh` runs, against the **RUNNING** image ids,
and verified by id match rather than by the tag existing:

```
docker tag c6c9ec2edce7 meddoc-pro-transcribe-md:pre-b7-20260811
docker tag 0c5a78e163e4 meddoc-pro-transcribe-md-worker:pre-b7-20260811
```

⚠️ **The migration does NOT roll back with the image, and cannot.** Postgres has
no `ALTER TYPE … DROP VALUE`, so the three enum labels are permanent from the
moment this deploy applies. That is accepted and is why three was a considered
number: an unused enum label costs nothing, and the alternative — a single label
with the outcome buried in metadata — would have been cheaper now and
unqueryable forever.

Rolling the IMAGE back removes the route. Nothing else needs undoing, because
nothing else changed.
