### Two things that must specifically NOT be true afterwards

- **`unitsSource` must NOT be `NOT NULL`.** If it is, the wrong migration ran.
  Step 2 is owed and unwritten *deliberately*: between step 3 (migrate) and step
  6 (recreate), the previous image is still serving and still writing usage rows
  it has never heard of the column for. A NOT NULL with no default would fail
  every one of those inserts — and quietly, because `logApiUsage` is
  fire-and-forget and swallows its errors to `console.warn`.
- **`unitsSource` must NOT carry a `DEFAULT`.** A provenance column defaulting to
  the trusted value is fail-open — the standing ruling of 2026-08-08. The
  obligation lives in the TypeScript type, so a new writer fails to *compile*.

## WHAT WOULD MAKE THIS CHECK FAIL — said plainly, so it can

1. **Migrations land at anything but 92**, or the applied name is not
   `20260808020000_b0_units_source`.
2. **`unitsSource` comes back NOT NULL, or with a default** — either means the
   fail-open shape this whole item exists to prevent has shipped.
3. **Any NULL `unitsSource` survives** the backfill. The migration's own
   `RAISE EXCEPTION` guard should abort the deploy first; if a NULL reaches the
   post-check instead, the guard did not run.
4. **`api_usage_events` ≠ 1312 or `ai_calls` ≠ 1122** — the migration would have
   written rows, which it has no business doing.
5. **Any clinical count moves**: visits ≠ 26, patients ≠ 15, signed ≠ 16,
   users ≠ 196. This is the row that is never omitted.
6. **Fewer than 9 healthy containers**, or any co-tenant status differing from
   the baseline line.
7. **An image id that did not change** — the deploy did not actually recreate
   that service, and the new code is not running.

## Rollback

`:pre-b0a-20260808`, cut and digest-verified above. Reverting the code alone is
sufficient: the column is nullable with no default, so a pre-B0-a image writing
against the migrated schema simply leaves `unitsSource` NULL. That is the
fail-closed-by-type posture behaving as designed — **the database's guarantee is
weaker than the type's until step 2 lands**, and that window is precisely why
step 2 is not in this deploy.
