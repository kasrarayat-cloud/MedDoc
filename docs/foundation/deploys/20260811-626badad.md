### ⚠️ ASSERTION 7 IS THE FAIL-CLOSED ARM, AND 503 IS THE PASS

This is the same argument step 1 made for its webhook, pointed at the outbound
route, and the number to read twice is the same one.

- **503 means the route exists and refused** — `decideCheckout` classified
  `STRIPE_SECRET_KEY` as `absent` and returned `not_configured` before anything
  else ran. No Stripe client is constructed, no network call is made.
- **A 400 would be the finding**, because 400 is what a *configured* environment
  returns for a bad amount or an unclassifiable key — so a 400 here would mean a
  Stripe secret key is set in production, which nothing in this programme has
  authorised and which the FOUNDATION guardrail forbids (TEST MODE ONLY).
- **A 401 would also be the finding**, but a different one: it would mean the
  probe reached the auth check, which is *before* the configuration check by
  design. The route authenticates first, so an unauthenticated probe should give
  **401**… and this is the part worth stating in advance rather than
  rationalising afterwards.

⚠️ **SO ASSERTION 7 IS DECLARED AS `401 OR 503`, AND THE DISTINCTION IS RECORDED
NOW.** The route's order is AUTHENTICATE → rate-limit → body → decide, so an
unauthenticated probe is refused at step 1 with **401** and never reaches the
configuration check. A **503** would mean the probe was somehow authenticated,
which it is not. **The pass condition is therefore: NOT 404, and NOT 400.**
404 means the route did not ship; 400 means a key exists in production. Either
is the finding. Writing this down before the probe is the point — after the fact,
both 401 and 503 have a comfortable story available to them.
