# §2.5 AUTHOR ROWS — PR #1036, ruling #210

**Written at PR-OPEN time, before the act**, per the ADMIN-1 board filing and
ruling #184: a passenger without author rows is a FINDING, not a pass.

**Lane:** Design/Admin. ⚠️ **THIS PR CARRIES A MIGRATION** —
`20260907040000_admin5_last_owner_trigger`.

    CREATE OR REPLACE FUNCTION users_is_active_owner("users") RETURNS boolean   -- sql IMMUTABLE
    CREATE OR REPLACE FUNCTION users_last_owner_guard()       RETURNS trigger   -- plpgsql
    CREATE CONSTRAINT TRIGGER "users_last_owner_guard_after_write"
        AFTER UPDATE OR DELETE ON "users"
        DEFERRABLE INITIALLY IMMEDIATE FOR EACH ROW
    CREATE CONSTRAINT TRIGGER "users_no_orphan_member_after_insert"
        AFTER INSERT OR UPDATE ON "users"
        DEFERRABLE INITIALLY IMMEDIATE FOR EACH ROW
    + a DO $verify$ block asserting its own trigger and function counts

⚠️ **IT ADDS NO COLUMN, NO TABLE AND NO ENUM VALUE, SO IT IS REVERSIBLE** — this
migration changes what is REFUSED, not what is stored, and nothing depends on the
functions existing.

**THE ROLLBACK, CORRECTED UNDER RULING #248 — IT WAS WRONG IN TWO WAYS.** It read
`DROP TRIGGER users_last_owner_guard_before_write ON users;`, which

  1. **names a trigger that does not exist.** The shape moved to a CONSTRAINT
     trigger and the name became `..._after_write`; the declared command errors
     out verbatim with `trigger "users_last_owner_guard_before_write" ... does
     not exist`. ⚠️ **A rollback nobody ran is a rollback nobody knows is
     broken** — and it would first be run in the one situation where there is no
     time to debug it.
  2. **covers ONE of the TWO triggers this migration creates.** Dropping only the
     removal guard leaves `users_no_orphan_member_after_insert` armed, so INSERTs
     and unsuspends into a zero-owner practice would still be refused. That is
     not "the prior behaviour exactly".

    -- the CORRECT rollback: both triggers, by their real names
    DROP TRIGGER IF EXISTS "users_last_owner_guard_after_write"  ON "users";
    DROP TRIGGER IF EXISTS "users_no_orphan_member_after_insert" ON "users";

The four functions may be left in place — they are pure, referenced by nothing
else, and dropping them is not required to restore behaviour. ⚠️ **Verify a
rollback by the count it leaves behind, not by the command exiting 0:**

    SELECT count(*) FROM pg_trigger t JOIN pg_class c ON c.oid=t.tgrelid
     WHERE NOT t.tgisinternal AND c.relname='users';   -- must be 0

⚠️ **IT IS A CONSTRAINT TRIGGER, NOT A `BEFORE` ROW TRIGGER, AND THAT CHANGED
AFTER THE ROWS WERE FIRST WRITTEN.** The `BEFORE` form — ruling #210's literal
wording — was measured against the E2E suite's own teardown
(`tests/e2e/helpers/cleanup.ts:99`) and **refused it**: a row trigger judges each
row before the statement's other rows are applied, so tearing a whole synthetic
practice down in one `DELETE` looked like abandoning its members. It was also
**order-dependent**, which is worse than wrong. The rows below are unaffected —
the counts in C1/C2/C3 are identical for either shape, and C1 was re-measured
against the new one — but the change is recorded here rather than left for a
reader to notice in the diff.

⚠️ **AND `prisma migrate diff` REPORTS NO DRIFT EITHER WAY.** Triggers are
invisible to Prisma's schema model, so `schema.prisma` is untouched and the
usual "did the schema move" instinct will report nothing. The trigger's presence
is asserted by the migration's own `DO $verify$` block and by row **1036-C1**,
because nothing else in the pipeline can see it.

## ⚠️ CI NOW PROVES THE BEHAVIOUR, WHICH IT DID NOT WHEN THESE ROWS WERE WRITTEN

The headline finding of this change's own adversarial pass was **"nothing runs
either proof in CI"**. That is now closed, and it changes what these rows are
resting on.

| where | what it proves | blocking? |
|---|---|---|
| `unit` job | the SOURCE agrees with itself — one predicate, one definition, 14 arms | yes |
| `e2e` job, after `db-migrate` | the **BEHAVIOUR** — 33 deterministic arms against a real Postgres carrying the real migration | **yes** |
| `e2e` job | the advisory lock's 2×2, with its own negative control | **on refutation only** |

⚠️ **THE RACE STEP HAS THREE OUTCOMES AND CI KEEPS THEM APART.** Exit 0 = every
predicted cell held. Exit 1 = a prediction was **refuted**, which fails the job.
**Exit 2 = CANNOT-TELL** — the two transactions never overlapped on that runner,
so the negative control was never given the chance to fire. *"The race did not
happen here"* and *"the lock is redundant"* are different facts, and the harness
distinguishes them with an **overlap witness taken from the racers' own
transaction intervals**. Treating them alike is how a flaky red becomes a re-run
and then a habit.

**The arms run BEFORE any seed**, so a failure there is unambiguous: the
migration ran and the trigger does not behave. Every arm rolls back its own
fixture, so the database the seeds then use is byte-unchanged.
