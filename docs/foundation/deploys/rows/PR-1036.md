# §2.5 AUTHOR ROWS — PR #1036, ruling #210

**Written at PR-OPEN time, before the act**, per the ADMIN-1 board filing and
ruling #184: a passenger without author rows is a FINDING, not a pass.

**Lane:** Design/Admin. ⚠️ **THIS PR CARRIES A MIGRATION** —
`20260907040000_admin5_last_owner_trigger`.

    CREATE OR REPLACE FUNCTION users_is_active_owner("users") RETURNS boolean   -- sql IMMUTABLE
    CREATE OR REPLACE FUNCTION users_last_owner_guard()       RETURNS trigger   -- plpgsql
    CREATE CONSTRAINT TRIGGER "users_last_owner_guard_after_write"
        AFTER UPDATE OR DELETE ON "users"
        DEFERRABLE INITIALLY IMMEDIATE FOR EACH ROW
    CREATE CONSTRAINT TRIGGER "users_no_orphan_member_after_insert"
        AFTER INSERT OR UPDATE ON "users"
        DEFERRABLE INITIALLY IMMEDIATE FOR EACH ROW
    + a DO $verify$ block asserting its own trigger and function counts

⚠️ **IT ADDS NO COLUMN, NO TABLE AND NO ENUM VALUE, SO IT IS REVERSIBLE** —
`DROP TRIGGER users_last_owner_guard_before_write ON users;` restores the prior
behaviour exactly, and nothing depends on the functions existing. That is
deliberate: this migration changes what is REFUSED, not what is stored.

⚠️ **IT IS A CONSTRAINT TRIGGER, NOT A `BEFORE` ROW TRIGGER, AND THAT CHANGED
AFTER THE ROWS WERE FIRST WRITTEN.** The `BEFORE` form — ruling #210's literal
wording — was measured against the E2E suite's own teardown
(`tests/e2e/helpers/cleanup.ts:99`) and **refused it**: a row trigger judges each
row before the statement's other rows are applied, so tearing a whole synthetic
practice down in one `DELETE` looked like abandoning its members. It was also
**order-dependent**, which is worse than wrong. The rows below are unaffected —
the counts in C1/C2/C3 are identical for either shape, and C1 was re-measured
against the new one — but the change is recorded here rather than left for a
reader to notice in the diff.

⚠️ **AND `prisma migrate diff` REPORTS NO DRIFT EITHER WAY.** Triggers are
invisible to Prisma's schema model, so `schema.prisma` is untouched and the
usual "did the schema move" instinct will report nothing. The trigger's presence
is asserted by the migration's own `DO $verify$` block and by row **1036-C1**,
because nothing else in the pipeline can see it.

## THE BASELINE, CAPTURED BEFORE THE ACT

Read from **production** at PR-open, 2026-09-07, by `SELECT` only. Every row
below is judged against these, and they were written down while they were still
true — which is the entire product §2.5 buys.

    triggers_on_users = 0     triggers_all = 4     guard_functions = 0
    visits = 58               signed = 40
    users  = 198              practices = 199
    practices with members and ZERO active OWNERs = 6

⚠️ **THE LAST NUMBER IS THE ONE THAT WOULD BE EASY TO READ AS A DEFECT AND IS
NOT.** Six practices are already in the state this trigger forbids creating.
That is why exemption 1 exists, and why row **1036-N3** asserts the number does
NOT move: the trigger prevents new violations and is deliberately silent about
existing ones. A migration that "fixed" them would be rewriting user rows nobody
asked it to touch.

## MUST CHANGE

| # | row | before | after | falsifier |
|---|---|---|---|---|
| **1036-C1** | user-defined triggers on `users` — `SELECT count(*) FROM pg_trigger t JOIN pg_class c ON c.oid=t.tgrelid WHERE NOT t.tgisinternal AND c.relname='users'` | **0** | **2** | if it stays 0 the migration ran and did nothing, and every claim in this PR is about code that is not enforcing anything. This is the ONLY row that can detect that — Prisma cannot. |
| **1036-C2** | user-defined triggers database-wide (`WHERE NOT tgisinternal`) | **4** (all on `ledger_entries`) | **6** | catches the trigger landing on the wrong relation — C1 alone would also pass if `users` gained a *different* trigger |
| **1036-C3** | the four guard functions in `pg_proc` — `users_last_owner_guard`, `users_is_active_owner`, `users_is_live_member`, `users_no_orphan_member` | **0** | **4** | the trigger cannot be created without them, so a 1 here means a partial apply |
| **1036-C4** | `POST /api/admin/users/[id]/suspend` and `.../soft-delete` on a practice's last active owner | **200**, the write lands | **409** `LAST_OWNER` | the friendly refusal is absent and the caller gets a raw Postgres error in a 500 instead of a sentence naming the remedy |

## MUST NOT CHANGE

| # | row | expectation | falsifier |
|---|---|---|---|
| **1036-N1** | **CLINICAL COUNTS — never omitted, per §2.5.** `transcribe_visits` total, and those with `signedAt IS NOT NULL` | **exactly as at baseline** | a deploy that moves a visit or signature count has done something nobody asked for. This migration touches no clinical table at all, so ANY movement is the finding regardless of the explanation available afterwards. |
| **1036-N2** | `users` row count, and `practices` row count | **198 / 199**, unchanged | the migration creates functions and a trigger and writes no rows; a change means it did something it was not asked to |
| **1036-N3** | practices with members but **zero active OWNERs** | **6**, unchanged | ⚠️ **the trigger must not RETROSPECTIVELY fix or break existing data.** A drop to 0 would mean something rewrote rows; a rise would mean the predicate moved under us |
| **1036-N4** | every `users` row remains writable — an unrelated `UPDATE` (e.g. `forceLogoutAt`) on a member of one of those 6 zero-owner practices | **succeeds** | exemption 1 has failed and the guard against lockout has created a lockout. This is the single most likely way this migration causes an outage. |
| **1036-N5** | `POST /api/settings/delete-account` for a **solo** practice owner | **succeeds**, practice torn down | exemption 2 has failed and a shipped self-service feature is broken for most practices |
| **1036-N6** | `schema.prisma` | **byte-unchanged** | a trigger that required a schema change would mean it was modelled as something else |
| **1036-N7** | the full unit suite | **green, and the number stated in the PR body is the one the suite produces** | ⚠️ a stale count here is the defect this lane found in PR #1018's own rows file; do not copy a number forward |

⚠️ **C1/C2/C3 WERE CORRECTED AFTER THE ADVERSARIAL PASS, AND THE ORIGINAL
NUMBERS ARE NAMED RATHER THAN QUIETLY REPLACED.** They read `0 → 1` trigger,
`4 → 5` database-wide and `0 → 2` functions, which was true of the shape written
at PR-open. The pass found the invariant needed an INSERT arm and a live-member
predicate, so the migration now creates **two** triggers and **four** functions.
Re-measured on the isolated QA stack against the shipped file, not edited to
match a hope. **A declaration whose numbers drift from the change it declares is
the defect this lane measured in another PR's rows file the same night** — so it
is corrected here, in the commit that changes the counts.

## VERIFY — structural, mutating nothing

    # C1 / C2 / C3 — the trigger and its functions exist, on the right relation
    docker exec -i meddoc-pro-postgres-1 psql -U meddoc -d meddoc -X -c "
      SELECT c.relname, t.tgname FROM pg_trigger t JOIN pg_class c ON c.oid=t.tgrelid
       WHERE NOT t.tgisinternal ORDER BY 1,2;
      SELECT proname FROM pg_proc WHERE proname IN ('users_last_owner_guard','users_is_active_owner');"

    # N1 — the clinical counts, read but never written
    docker exec -i meddoc-pro-postgres-1 psql -U meddoc -d meddoc -X -c "
      SELECT count(*) AS visits, count(*) FILTER (WHERE \"signedAt\" IS NOT NULL) AS signed
        FROM transcribe_visits;"

    # N2 / N3 — population, and the zero-owner practices that exemption 1 protects
    docker exec -i meddoc-pro-postgres-1 psql -U meddoc -d meddoc -X -c "
      SELECT (SELECT count(*) FROM users) AS users, (SELECT count(*) FROM practices) AS practices;
      SELECT count(*) FROM (
        SELECT p.id FROM practices p JOIN users u ON u.\"practiceId\"=p.id GROUP BY p.id
         HAVING count(*) FILTER (WHERE users_is_active_owner(u)) = 0) z;"

exercised against production. Both are covered on the isolated `meddoc-qa`
