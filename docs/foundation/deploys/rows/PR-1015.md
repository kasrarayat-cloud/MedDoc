# §2.5 AUTHOR ROWS — PR #1015, REVIEW-DEFAULTS item 1

**Written at PR-OPEN time, before the act**, per the ADMIN-1 board filing and
ruling #184: a passenger without author rows is a FINDING, not a pass.

**Lane:** Design/Admin. ⚠️ **THIS PR CARRIES A MIGRATION** —
`20260906000000_review_defaults_scaffold_insert`.

    ALTER TYPE "AuditAction" ADD VALUE IF NOT EXISTS 'DEFAULT_INSERTED_BY_DOCTOR';
    ALTER TYPE "AuditAction" ADD VALUE IF NOT EXISTS 'DEFAULT_INSERT_UNDONE';
    ALTER TABLE "template_twin_field_overrides"
      ALTER COLUMN "selectedOptionOrdinal" DROP NOT NULL,
      ALTER COLUMN "optionValue"          DROP NOT NULL,
      ADD COLUMN  "overrideKind" TEXT NOT NULL DEFAULT 'option',
      ADD COLUMN  "insertedText" TEXT;
    + CHECK template_twin_field_overrides_kind_shape

⚠️ **THE TWO ENUM VALUES ARE PERMANENTLY IRREVERSIBLE.** Postgres has no
`ALTER TYPE … DROP VALUE`. Two are added rather than one because an undo
emitted under the insert's label makes every action-level rollup count a
reverted assertion as an assertion — which defeats the only thing the
irreversible add was bought for.

## MUST CHANGE

| # | row | before | after | falsifier |
|---|---|---|---|---|
| **1015-C1** | `AuditAction` label cardinality | **158** | **160** | the migration's whole enum half; if it does not move, the labels exist only in TypeScript and every write of them is swallowed into one `console.error` |
| **1015-C2** | `template_twin_field_overrides` columns `overrideKind`, `insertedText` | absent | present | the feature has nowhere to store the doctor's assertion |
| **1015-C3** | constraint `template_twin_field_overrides_kind_shape` | absent | present | without it a row satisfying neither arm is storable, and nullability has removed the guarantee the column types used to give |
| **1015-C4** | `your-blanks-panel` present in the shipped server bundle | **0 files** | **≥ 1 file** | the doctor-facing half never reached the image |

## MUST NOT CHANGE

| # | row | expectation | falsifier |
|---|---|---|---|
| **1015-N1** | rows in `template_twin_field_overrides` | **unchanged** | the migration adds columns and migrates NO data; any row-count movement means something wrote during the deploy |
| **1015-N2** | every existing row's `overrideKind` | `'option'` (the column default) | an existing dropdown correction re-classified as a scaffold insert would be read back through the wrong arm and dropped fail-closed |
| **1015-N3** | ⚠️ **stored `overridesSha256` values stay VALID for existing option rows** | the identity of a legacy `option` row is byte-identical to the pre-deploy formula | **this is the row the adversarial pass produced.** The first version hashed a 4-tuple for every kind, so every visit carrying a dropdown correction would read STALE at once and re-fill — and the migration repairs no data. The gate arm recomputes the pre-diff sha independently |
| **1015-N4** | clinical counts — visits, patients, signatures | unchanged | never omitted, per §2.5 |
| **1015-N5** | `AuditAction` labels other than the two added | unchanged | an `ADD VALUE` that reordered or renamed anything would corrupt every historical row |

## VERIFY — structural, mutating nothing

⚠️ **THE DISCRIMINATOR IS STATED.** `your-blanks-panel`, `overrideKind` and
`DEFAULT_INSERT_UNDONE` are all NEW in this range; each measures **0** in the
image running today.

    -- C1
    SELECT count(*) FROM pg_enum e JOIN pg_type t ON t.oid=e.enumtypid
      WHERE t.typname='AuditAction';                                    -- 160

    -- C1, by name
    SELECT enumlabel FROM pg_enum e JOIN pg_type t ON t.oid=e.enumtypid
      WHERE t.typname='AuditAction'
        AND enumlabel IN ('DEFAULT_INSERTED_BY_DOCTOR','DEFAULT_INSERT_UNDONE');

    -- C2 / C3
    SELECT column_name FROM information_schema.columns
      WHERE table_name='template_twin_field_overrides'
        AND column_name IN ('overrideKind','insertedText');             -- 2 rows
    SELECT conname FROM pg_constraint
      WHERE conname='template_twin_field_overrides_kind_shape';         -- 1 row

    -- N1 / N2
    SELECT count(*)                          FROM template_twin_field_overrides;
    SELECT DISTINCT "overrideKind"           FROM template_twin_field_overrides;  -- {option}

    -- C4, in the shipped bundle
    docker exec meddoc-pro-transcribe-md-1 sh -lc \
      "grep -rl 'your-blanks-panel' /app/apps/transcribe-md/.next/server | wc -l"

⚠️ **POSITIVE CONTROL FIRST, and it is NOT the check.** Grep the bundle for
`CANNOT_CHANGE_AN_OWNER` — it shipped with #1010 and exists in **both** images,
so it proves the grep reaches the bundle while proving nothing about this PR.
Using it as the verification row would be exactly the non-discriminating check
the board filing warns about.

**No real doctor's visit is a smoke target.** The full insert / undo / re-render
walk belongs on QA against a byte-identical build. In production this is DOM
presence on `/visits/[id]` and the structural queries above, mutating nothing.

## ⚠️ WHAT THESE ROWS CANNOT DETECT, SAID PLAINLY

A derived row cannot see the thing this PR is actually about: whether a stored
default ever lands on a field the encounter DENIED. That is not observable from
a schema or a bundle — it needs the clinical walk on QA, and the arms in
`gate-review-defaults-insert` are what stand for it between deploys. Named here
rather than implied as covered.
