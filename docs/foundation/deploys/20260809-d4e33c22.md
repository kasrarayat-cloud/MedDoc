## The one-line summary

**This is a code-and-migration deploy whose migration only WIDENS what the
database will accept and writes no row.** `DROP NOT NULL` cannot reject an
existing row and cannot modify one; the `ADD CONSTRAINT` is satisfied by all 1312
rows as they stand. So rows 5 through 15 must **all** be byte-identical, and the
only movement anywhere is the migration count, two catalog facts, and two image
ids.

⚠️ **Row 10 is the one to read carefully, and it is the inverse of B1-a's.** B1-a
added a column and declared every historical value must stay **NULL**. This
migration makes a populated column *nullable* and declares every historical value
must stay **NON-NULL**. Both say the same thing — *the deploy changes what is
possible, never what is recorded* — and in this direction the dangerous outcome
is a historical vendor id being cleared, which would destroy the correlation data
B1-a exists to collect.

⚠️ **Row 14 pins the thing the NEXT step will move.** The whole point of steps 3
and 4 is to produce real `ai_calls.requestId` values. Pinning it at 1112 NULL now
means step 4's numbers are attributable to the smoke and not to this deploy —
without this row, the two changes would be indistinguishable afterwards.

⚠️ **The migration's own abort guard is expected to pass silently.** It refuses
if any row carries an id on a non-vendor provenance. The census above says zero
such rows exist, so a `RAISE EXCEPTION` from `[b1b-step2]` would mean the
population changed between 18:13Z and the migration — itself the finding.
