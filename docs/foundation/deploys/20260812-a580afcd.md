## WHAT WOULD MAKE THE POST-DEPLOY CHECK **FAIL**

Any one of these is a FINDING, whatever explanation is available afterwards:

- migrations ≠ **101**, or the new row is not the `b7s3c` one
- `PROMO_GRANT_CREDITED` still absent from `pg_enum` after the deploy — the
  migration ran but the enum did not move
- **any** movement in `ledger_entries`, the promo sum, or the paid sum
- **any** `PROMO_GRANT_CREDITED` row in `audit_logs`
- **any** movement in visits / signed / patients
- practice counts away from 197 / 175
- `BILLING_ENFORCED` set in either container
- any co-tenant status away from its baseline
- either image id unchanged (the deploy did not actually replace the service)

⚠️ **A difference not in this list is THE FINDING**, however plausible its
after-the-fact story.

## ROLLBACK

Tag cut against the **running** image ids before anything is recreated, per the
runbook, and digest-verified. The migration is an `ALTER TYPE … ADD VALUE`;
**Postgres has no `DROP VALUE`, so the label is permanent** — an image rollback
returns the code, not the enum. That is accepted and is why the label count was
argued down to one.
