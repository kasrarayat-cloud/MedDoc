## ⚠️ THE CERTIFIED ROW'S LITERAL WAS WRONG — corrected, with the reason

The declared row read:

    certificationStatus='certified'

**The enum has no such value.** Measured from `pg_enum`:

    RECOGNIZED · NEEDS_CONFIRMATION · UNSUPPORTED · CERTIFIED · QUARANTINED

Run as written, the row does not return a wrong number — it **errors**:

    ERROR: invalid input value for enum "TemplateTwinCertificationStatus": "certified"

⚠️ **THAT IS THE LUCKY DIRECTION, AND IT IS THE ONLY REASON THIS IS CHEAP.**
Postgres refuses an unknown enum literal in a comparison, so the row fails
loud. Had `certificationStatus` been a plain `text` column — which is exactly
how the sibling `AuditAction` mistakes in this house's canon presented — the
same query would have returned **`0`**, and a `0` is precisely what the row
asserts. **The post-deploy judgement would have read "✅ 0 certified" while
measuring nothing at all**, on the one row that exists to prove a deploy cannot
certify a template nobody confirmed.

This is AGENTS.md's *"ask what SHAPE the data is before asking how much of it
there is"*, and MASTER.md's measurement-discipline ruling, arriving inside a
§2.5 declaration rather than inside a recon script.

**AND THE HONEST LIMIT, STATED SO THE ROW IS NOT READ WIDER THAN IT IS:** with
`template_twin_compiled_versions` at **0**, the CERTIFIED count is **entailed by
the parent being empty** — no filter discriminated anything. It is a true zero
and a vacuous one. It becomes a real measurement the moment a doctor uploads a
`.docx` (RC-2 compiles on every upload), and **that is the case the row is
actually for.** Correcting the literal now is what makes it work then.
