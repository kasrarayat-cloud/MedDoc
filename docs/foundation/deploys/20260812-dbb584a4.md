### ⚠️ ASSERTION 4 IS THE ONE THAT CARRIES THE ITEM

`ledger_entries` must still hold **0 rows** afterwards, and that is a stronger
claim here than it looks, because this is the first deploy of code whose entire
subject is that table.

Rulings **89(e)** and **90(d)** both depend on the zero-row state — an
append-only table cannot take a new column later without either a fail-open
DEFAULT or a backfill UPDATE, so *"the table is empty"* is what made B5's
`bucket` and B6's `pricing` free. Ruling **94(e)** defers B7 step 3's 197-row
promo grant behind B8 for exactly that reason.

**So a single row appearing here would not be a small surprise — it would spend
a budget three rulings are built on.** It cannot happen: this deploy adds a
READER and a pure function, and the only writers are B6's `commitVisitCharge`
and B7's webhook, neither of which gains a caller. The assertion exists because
that argument is a claim about code, and §2.5 exists to check claims about code
against the database.

### ⚠️ A NOTE ON HOW THESE NUMBERS WERE MEASURED

The first attempt at the baseline nested the SQL inside two layers of double
quotes under `shell=True`. The shell ate it, `psql` received nothing, and the
script **printed an empty DB section as though it were a result**. Had that
gone unnoticed, this declaration's must-not-change table would have been written
from no measurement at all.

The rewritten script passes the SQL as an argv element and **runs a positive
control first** (`SELECT 'control', 1`, checked against its known answer), so a
connection that cannot answer is distinguishable from a table that is empty.
That control immediately earned itself: the second attempt failed with
`role "postgres" does not exist` — the production role is `meddoc` — which the
silent version would have rendered as another blank section.

**An emptiness test over a set whose boundary was never established is this
project's named recurring defect**, and it arrived here in the most ordinary
way available: a quoting bug in a baseline script.
