## WHAT #754 CHANGES, IN ONE PARAGRAPH

`runTemplateTwinSyntheticTest` treated a pinned synthetic note as valid on
PRESENCE (`const pinValid = !!pinned`). When the note's encounter/template shas
no longer matched and no sibling supplied a fresh one, the old code fell through
**still holding the stale note**, so certification ran against a note generated
from a *different* encounter. Measured by its author on production: the owner's
template certified against a note dated `2026-08-18T23:19:50Z`, and fills went
**7 → 5** — a refusal that read as *"your form does not fill"* when the truth was
*"the model never saw this encounter"*. The fix adds a key check and, when the
key does not match, **NULLs the note in the same statement that re-keys the
extraction**, so a mislabelled pin cannot be silently re-keyed into looking
current.

⚠️ **THAT NULL IS A WRITE, AND IT IS WHY ROWS 11 AND 12 EXIST.** It happens only
inside `runTemplateTwinSyntheticTest`, i.e. on a certification attempt. **A
deploy does not call it.** If those rows move at deploy time, that is the
finding.
