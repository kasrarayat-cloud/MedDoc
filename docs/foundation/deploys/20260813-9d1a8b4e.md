## WHAT WOULD MAKE THE POST-DEPLOY CHECK **FAIL**

Any one of these is a FINDING, whatever explanation is available afterwards:

- either image id unchanged — the deploy did not replace the service
- `billing-failure.ts` absent from the worker image, or `observeFailedVisitUsage`
  absent from its `worker.ts` — a green deploy over a stale image
- migrations ≠ **101**
- **any** movement in `ledger_entries` (175), the promo sum, or the paid bucket
- **any** movement in visits / signed / patients
- any visit in `FAILED`, or any non-NULL `failureCategory`
- practices ≠ 197
- `BILLING_ENFORCED` set in either container
- any co-tenant status away from its baseline
- an `api_usage_events` jump not accounted for by a visit

⚠️ **A difference not in this list is THE FINDING**, however plausible its
after-the-fact story.

## ⚠️ WHAT A SILENT DEPLOY MEANS — declared FIRST, so it cannot be spun LATER

**The expected outcome of this deploy is that nothing visible happens.** The
seam runs only inside the worker's FAILED branch, and production has held **zero**
FAILED visits, ever. So:

> **The absence of a `failure cost` log line after this deploy is NOT evidence
> that the seam works, and it is NOT evidence that it is broken. It is evidence
> of nothing at all**, because the branch is not reached.

This is written down in advance precisely because the post-deploy transcript
will be quiet, and a quiet transcript is the easiest thing in the world to read
as success. **The behavioural proof that the seam works does not live here — it
lives on QA**, where session 04 walked three arms against a rebuilt worker image
on 2026-08-13 (`scripts/qa/b8-failure-cost-on-qa.ts`), measured `ledger_entries`
0 → 0 in both postures, and found two defects doing it. This deploy inherits that
proof; it does not re-establish it, and it must not be reported as if it did.

**What this deploy legitimately establishes is narrower and worth stating
plainly:** that shipping the unflagged seam to production moves no money, no
clinical row, and no co-tenant. That is the MUST-NOT-CHANGE table, and it is a
real claim — it is the first time an unflagged billing seam has run here.
