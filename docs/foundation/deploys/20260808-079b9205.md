## What would make this check FAIL

Stated now, so the comparison has one correct answer fixed before the evidence
exists:

1. **Any clinical count moves.** 26 / 15 / 16 / 196. A code-and-migration deploy
   that touches a visit, patient, signature or user count has done something
   nobody asked for.
2. **`api_usage_events` is not 1312.** This migration alters a column and adds a
   constraint. It must not create, delete or duplicate a usage row. A *fall*
   would mean the migration destroyed metered history; a *rise* means something
   wrote during the window, which is possible in principle and must then be
   explained rather than waved past — the newest row is three days old, so a new
   one appearing during a deploy is itself the finding.
3. **Migrations are not exactly 93**, or the applied name differs.
4. **`is_nullable` is still `YES`** — the migration silently did not take.
5. **The CHECK is absent**, or its definition is not the two ruled values.
6. **`unitsSource` has acquired a DEFAULT.** Nothing in this change adds one; if
   one appears, something other than this migration touched the column, and it is
   the exact fail-open the ruling forbids.
7. **Any NULL or off-domain `unitsSource` row exists afterwards.** The migration
   raises rather than proceeding, so a non-zero count here means the abort guard
   did not run.
8. **Only one image id changes.** Both services rebuild; one moving alone means a
   partial recreate — the documented "half the stack on the previous
   invocation's env" failure.
9. **Any co-tenant status changes.** Not ours, and a change is a finding even if
   everything else is clean.
