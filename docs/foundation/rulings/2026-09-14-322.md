# Ruling #322 — 2026-09-14 (S2-4: the visit export renders on the doctor's original PDF page, driven by the certified twin's field values)

Recorded by the receiving session in its first commit, before building.

## #322 — OWNER-RULING (S2-4) — a PDF-origin visit export is the doctor's OWN page, filled by the certified twin's values; the structural styled render is the named-reason fallback; preview and export share one renderer

**STANDING.** The verbatim owner directive:

> for a PDF-origin template, the VISIT EXPORT renders on the original PDF page
> (the pdf-native coordinate fill) using the certified twin's field values — the
> twin decides what fills, the doctor's page decides how it looks. The structural
> twin's styled render is the FALLBACK only, with a named reason, when a value
> cannot be placed (overflow beyond the continuation-page rule, a control with no
> anchor). Preview and export must use the same renderer — arm it: the settings
> preview and a visit export of the same template are the same page shape.
> Deploy, judge, report once; the owner's colonoscopy form is the fixture.

### Measured state before the build (2026-09-14)

Two independent "native" systems, ruled to COEXIST under S2-3:

1. **pdf-native** (`src/lib/pdf-native/`) — a coordinate fill on the doctor's
   ORIGINAL PDF page. Cert = `styleProfile.pdfNativeCertified` + `pdfNativeAnchors`
   (+ stored canvas). `nativePdfExport` sources its per-region TEXT from
   `buildPdfFillTexts` (`note-to-texts.ts`): the generated note markdown split by
   `## heading`, matched to section LABELS, plus deterministic header fields. It
   reads NOTHING from the twin. Anchor keys are note-template slugs
   (`section.key` / `headerField.key`).
2. **Template Twin** (`src/lib/template-twin/`) — a semantic resolver that decides
   each field's VALUE for a visit (`processTemplateTwinVisit` →
   `FieldResolution[]`, keyed by `fieldId = ttf_…`, a salted structural hash), and
   renders the twin as a **structural DOCX** → Gotenberg PDF. For a PDF source the
   twin's "document" is the SYNTHESISED prose DOCX (S2 `pdfToProseDocx`), never the
   doctor's PDF page. It runs the fill ONLY for a **CERTIFIED** twin
   (`template-twin-fill-step.ts` `isCertifiedTwinTemplate`).

Export precedence today (`export/pdf/route.ts`): `nativePdfExport` FIRST; if it
declines, `resolveVisitDocx` → the twin DOCX → `renderVisitPdfFromDocx`.

**The two namespaces are disjoint** — pdf-native anchor keys are note-template
slugs; twin values are keyed by `fieldId`. The ONLY shared signal is the LABEL
(the field definition carries a `label`; the anchor carries the `label` it was
located by). So routing twin values onto the original page is a LABEL bridge.

⚠️ **The owner's own colonoscopy template is not yet a CERTIFIED twin.** Its
latest note_template (`cmu1tpvsj…`, 2026-09-14) is pdf-native-certified (12
anchors + canvas) and has a compiled twin with **21 field definitions but 0
certifications** — auto-certify declined on clinically-wrong mappings; the
owner's panel-confirm is pending (prior arc). So S2-4's twin-driven path cannot
FIRE on the owner's live form until that twin is certified. This ruling arms and
proves the architecture against the colon form as a FIXTURE; the live cert is a
separate, owner-gated step.

### What is built

- A LABEL bridge: the certified twin's `FieldResolution[]` for a visit, joined to
  its field definitions for the label, mapped onto the pdf-native anchors by
  normalized label → the `{ anchorKey → value }` fill map. The twin decides the
  value; the anchor decides where on the doctor's page it lands.
- `nativePdfExport`, for a PDF-origin template whose twin is CERTIFIED and has a
  fill manifest for the visit, uses the TWIN values (not the note-heading split).
  A non-twin or uncertified-twin template keeps the current note-heading behaviour
  (backward-compatible).
- **The named-reason fallback**: if a certified-twin value CANNOT be placed — a
  resolved field with a value but NO matching anchor, or content that overflows
  beyond the continuation-page rule — the export declines with a coded reason and
  the route falls back to the twin's STRUCTURAL styled render (the existing
  DOCX→Gotenberg path). No clinical value is dropped or silently misplaced.
- **Preview/export parity**: the settings note-format preview and the visit export
  fill the SAME original page through the SAME engine on the SAME stored anchors —
  the preview shows sample values, the export shows the twin's — same page shape.

### Design choices recorded (surfaced to the owner in the report)

1. **Uncertified twin → current behaviour.** S2-4's twin-driven values fire only
   when the twin is CERTIFIED. This keeps every existing export byte-stable until
   a twin is certified, and is why the owner's live colon form is unaffected until
   panel-confirm.
2. **"Cannot be placed" → whole-export styled fallback, not an addendum page.**
   The ruling names "a control with no anchor" as a fallback trigger, so a
   certified-twin field whose label matches no anchor routes the WHOLE export to
   the structural styled render (which can place every field), rather than the
   pre-S2-4 "Additional documentation" addendum page. This supersedes the addendum
   rule for the certified-twin PDF path only; the note-heading path is unchanged.

Flag-gated + fail-safe (a bridge/fill error falls back to styled with a coded
reason, never a 500, never a blocked visit). Own adversarial pass. Fixture: the
owner's blank colonoscopy form.
