## #210 — OWNER-RULING — THE LAST-OWNER INVARIANT IS A PROPERTY OF THE DATA, NOT OF ONE DOOR

**STANDING. Governs the ADMIN-5 lane from here; #200 still binds ADMIN-5's
invariant and proof, and this ruling moves where the invariant is ENFORCED.**

### THE INVARIANT, STATED ONCE

> **No write may leave a practice with zero active OWNERs.**

### WHY IT CANNOT LIVE IN A DOOR

It binds **every surface that can reduce a practice's active-owner count**:

- a **role change** (OWNER → CLINICIAN / TECH)
- a **deactivation**
- a **suspension**
- a **soft-delete**
- a **self-service account deletion**

Five doors today, and the set is open — the sixth is written by whoever adds the
next admin surface, and they will not read this file. **A guard per door is a
guard per door you remembered.** The invariant is a statement about the DATA, so
it is enforced where the data is.

### THE MECHANISM

**A `BEFORE UPDATE OR DELETE` trigger on the user row** refuses any write that
would leave that row's practice with zero active OWNERs. **The user row is the
one place all five doors pass through** — that is the whole argument for putting
it there, and it is a structural argument rather than a preference.

**The application guards REMAIN, and their job changes.** They are the
**friendly refusal**: the reason, in words the person can act on — *"transfer
ownership first"* — surfaced before the write is attempted. They stop being the
enforcement and become the explanation. A trigger produces a database error; a
database error is not a user experience.

### SCOPE, STATED SO IT IS NOT WIDENED OR NARROWED LATER

| surface | disposition |
|---|---|
| the database | **the trigger** — enforcement, all doors, no exceptions |
| transcribe-md role change / demotion | app-layer guard **already ruled** (ADMIN-5, #200) — kept, as the friendly refusal |
| transcribe-md admin **suspend** / **soft-delete** routes | **get the app-layer guard** — named explicitly, in scope |
| **meddoc-pro system-admin doors** | **OUT OF SCOPE.** That app is deleted and serves `410`. Recorded in **`KNOWN_UNGUARDED`** until the trigger makes them moot |

**`KNOWN_UNGUARDED` is the point of the fourth row.** An out-of-scope decision
that is not written down is indistinguishable, six weeks later, from a surface
nobody looked at. The record says: these doors were SEEN, they were judged
unreachable, and here is what would make that judgement stop being true.

### ⚠️ THE FK-RESTRICT ACCIDENT STOPS BEING LOAD-BEARING

Part of what has been holding this invariant up is a foreign key that happens to
refuse the delete. **That is not an invariant, it is a coincidence that has been
lucky**, and two things are wrong with leaning on it:

1. **It is about DELETE and says nothing about UPDATE** — and four of the five
   doors above are updates. A demotion, a deactivation, a suspension and a
   soft-delete are all UPDATEs, and a restrict-on-delete has no opinion about
   any of them.
2. **Nobody chose it.** It was a side effect of a relation someone declared for
   a different reason, which means the next person to change that relation for a
   third reason silently removes the guarantee, and nothing anywhere will say
   so.

**After #210 the trigger is the load-bearing thing and the FK is incidental
again.** If removing the FK-restrict would still leave the invariant standing,
the invariant is real.

### WHAT IS OWED

- **Its own §2.5 rows** — the trigger is a migration, and a migration-carrying
  deploy declares what MUST change and what must NOT before it runs.
- **Its own adversarial pass** on the finished diff.
- The clinical-count row is never omitted, per §2.5.

## #212 — OWNER-RULING — PR #1026 GETS ONE MORE PASS AFTER THE TRIGGER LANDS

**STANDING.**

With the **structural arm** and the **`DEMOTING_WRITERS` ratchet** in place, one
more pass runs on the finished diff — **after #210's trigger lands, not
before.**

### ⚠️ THE TRIGGER CHANGES WHAT THE HARNESS MUST PROVE

Before the trigger, the harness answers one question: *does the guard refuse?*

After the trigger there are **two enforcers in series**, and that is the exact
shape in which a green harness proves nothing about either one:

> **THE GUARD AND THE TRIGGER MUST EACH REFUSE ALONE.**

- Delete the app guard → **the trigger must still refuse.**
- Delete the trigger → **the app guard must still refuse.**

A suite that only ever exercises them together is green in three of the four
worlds it needs to distinguish, and cannot tell you which one it is in. **Each
arm must red on its own deletion** — that is the requirement, and it is the same
mutation discipline this programme already applies to a single guard, applied to
a pair.

**This is why the pass is ordered AFTER the trigger** rather than run now and
re-read later: a pass over a one-enforcer diff cannot see the two-enforcer
failure mode, and re-reading its report against a changed tree is how a finding
gets marked discharged by a measurement that never covered it.

## #213 — OWNER-RULING — THE #206 MARKER IS SESSION ID + START-TIME, NEVER `$$`

**STANDING. Amends #206. PR #1032's amendment is CORRECT and is adopted.**

**#206** specified that a lens sandbox carries a marker file naming *"its owner
session id and pid"*, and that the reaper refuses to remove one whose owner is
still alive.

> ⚠️ **`$$` IN A TOOL SHELL IS A FRESH SUBSHELL.** The pid it records belongs to
> a process that does not outlive the command that stamped it.

So an aliveness check against that pid answers a question about a process that
was already dead when the file was written — and it answers **"dead"**, which is
the direction that costs somebody their tree. **A guard that fails open, on a
timescale of seconds, is the guard #206 was written to replace.**

### THE MARKER, AS AMENDED

**The session id and the tree's start-time.** The session id is the identity
that actually spans the work; the start-time is what makes a stale marker
distinguishable from a live one.

### THE REFUSAL, AS AMENDED — AND THE `OR` IS LOAD-BEARING

> **The reaper refuses when the owner's marker is FRESH *OR* when ANY process
> holds the tree.**

Either condition alone is a guard with a hole:

- **marker-only** misses a live worker whose session stamped its marker long ago
- **process-only** misses a session between commands, which is most of the time

**The custom-file session implements this.** This session records it and **does
not touch that branch** — a peer can carry reasoning, never authority, and this
is the reasoning arriving with the owner's decision attached to it.

## #214 — OWNER-RULING — `shred` IS DELIBERATELY DENIED; THE GRANTED DOOR IS THE WRAPPER

**STANDING. Recorded by PR #1031.**

`AGENTS.md`'s close-out section names `shred -u -n 3 -z` as the instrument. **The
settings file denies it.** Both are correct, and the gap between them is the
finding:

> **`shred` is denied DELIBERATELY, per ruling #166 — a permission entry is a
> command-text PREFIX, so no path scope is safe.** A grant narrow enough to be
> safe cannot be written, so the grant is not written.

**The granted door is `bash scripts/reap-session-scratch.sh`.**

⚠️ **VERIFIED IN THIS COMMIT, per the standing rule that an entry naming an
instrument checks that instrument's GRANT in the same commit** — because a rule
and its grant live in different files, land in different PRs, and nothing checks
that the second followed the first:

```
$ python3 - <<'PY'   # over .claude/settings.json
allow: Bash(bash scripts/reap-lens-sandbox.sh:*)
allow: Bash(bash scripts/reap-session-scratch.sh:*)
deny:  Bash(shred:*)
PY
```

**So this ruling is not inert**, and the denial it records is measured rather
than remembered. This session uses the wrapper for the five `/tmp` files it is
closing out.
