## #176 — THE ADMIN ARC IS PINNED TO THE BOARD, AND BILLING IS DEFERRED TO A SESSION THAT DOES NOT EXIST YET

**OWNER RULING, 2026-09-04. STANDING.**
Received and recorded by the Design/Admin session in the commit that lands it,
per *"war-room rulings are recorded by the RECEIVING session, in its first
commit"*. The number is a **PROPOSAL until this row lands on `main`** — the
number-claim protocol at the head of `RULINGS.md`.

### The order, as given

Four named rows into the LIVE QUEUE, *"so nothing from the loop era is lost"*,
each with an owner and a slot, and a read-only recon on all four first.

| row | owner | slot |
|---|---|---|
| **ADMIN-1** practice multi-user | Design/Admin | **inside** ADMIN |
| **ADMIN-2** custom domain per practice | Design/Admin | ADMIN follow-up — recon first; ingress may be deploy-owner work |
| **ADMIN-3** specialty partitions | Design/Admin | ADMIN follow-up |
| **B8/B9** promo / pricing | **a dedicated billing session the owner opens** | after ADMIN |

The execution order is unchanged: **T3 → T2 → T4 → ADMIN**, carrying rows 1–3.

### Why billing is deferred rather than queued

The owner's own reason, recorded because it is the load-bearing one: **the promo
unit depends on the practice model.** ADMIN-1 decides what a "user" is inside a
practice, and the promo is denominated in exactly that noun. Building the
billing arc first would fix the denominator before the thing it counts exists.

⚠️ **No session below the owner may un-park it.** The trigger is *ADMIN lands*,
and it is written here so a later session cannot promote it on a feeling that
there is time — the failure the parked Q1 rows already record.

### ⚠️ THE RECON CONTRADICTED THE ORDER'S OWN HEADLINE FIGURE

The order says **"$10 per new user"**. The shipped code says **$10 per
PRACTICE**, and the code is the authority until the owner rules otherwise.

Verified twice, by two independent routes, before this was written down:

**Source.** `packages/ai/src/billing-grant.ts:141-143` —
`promoGrantKey(practiceId)` returns `` `grant:promo:practice:${practiceId}` ``,
used as the `idempotencyKey` on a globally-unique column, with
`PROMO_GRANT_MICRO_USD = 10_000_000n` (`:110`).

**Production, read-only.** `ledger_entries` holds **177** rows, **all** of kind
`grant`, summing **1,770,000,000 µUSD = $1,770.00 = 177 × $10**, across **177
DISTINCT practices** — exactly one grant each. Seat distribution of those 177:

| seats | practices | grant received |
|---|---|---|
| 1 | 175 | $10 |
| 5 | 1 | **$10** |
| 11 | 1 | **$10, not $110** |

No topup, usage, refund or adjustment row has ever existed.

**Why this is a finding and not a detail.** *A difference that is not in the
declaration is THE FINDING, whatever its explanation sounds like after the
fact.* Moving to per-seat is a change of shipped meaning, not an implementation
choice — and `ledger_entries` is **append-only in the database** (4 triggers, 6
CHECK constraints), so a wrong unit cannot be deleted, only offset. The billing
session must be handed this, not left to discover it.

### And the practice model is further along than the row implies

`enum PracticeRole { OWNER, CLINICIAN, TECH }` and `User.practiceRole` are
**already applied in production** behind a CHECK constraint, and invite
redemption already carries `(practiceId, practiceRole)` end to end with an E2E
proving it. **ADMIN-1 is therefore not a migration.** What is missing is the
reachable seat-minting (the only `inviteCode.create` in the tree sets neither
field) and enforcement past signing (one mutating surface of many).

⚠️ **The capability gap is not where it looks.** `note_templates` is RULED
doctor-scoped and deliberately not migrated, so **colleagues cannot share a note
format**. That is narrower than practice scope, so it is not a tenancy hole —
but it is a first-order product limitation, and changing it means re-opening a
ruling rather than fixing a bug.

### What this ruling does NOT decide, and must not be read as deciding

Four class-(a) questions are surfaced, not answered — one per row, and they are
the owner's:

1. **ADMIN-1** — who may invite and promote inside a practice. `OWNER` confers
   no power over `CLINICIAN` today; SPEC §4.1a/§4.1b rule signing and reading,
   neither rules administration.
2. **ADMIN-2** — QuillMD subdomain vs customer-owned apex. This single choice
   sets the entire cost: the apex route needs DNS-01, therefore a DNS API token,
   which is class (d) and absent.
3. **ADMIN-3** — filter or model. Restoring a board filter control would reverse
   ruling R3.8.
4. **B8/B9** — per practice or per seat, per the contradiction above.

## #177 — THE PRICING UNIT IS THE PROVIDER SEAT, AND THE WELCOME CREDIT FOLLOWS IT

**OWNER RULING, 2026-09-04. STANDING.** Given in direct answer to the
contradiction #176 recorded — the order said *"$10 per new user"*, the shipped
code said $10 per practice, and this settles it.

| | ruled |
|---|---|
| **pricing unit** | **per provider SEAT** |
| **welcome credit** | the SAME unit — **$10 per seat** |
| **cap** | **PROPOSAL: 10 seats** — stated, not yet ruled |
| **applies to** | **NEW grants only** |
| **the 177 existing per-practice grants** | **stay as recorded** |

**Executed by the dedicated billing session**, not by this arc — B8/B9 remains
parked behind *ADMIN lands*, because the seat is defined by the practice model
ADMIN-1 settles. Recording the ruling does not un-park the item.

### Why the existing grants stay, stated as a property rather than as leniency

`ledger_entries` is **append-only in the database** — 4 triggers and 6 CHECK
constraints — so nothing there can be deleted, only offset. The grant is keyed
`grant:promo:practice:<id>` on a globally-unique `idempotencyKey`
(`billing-grant.ts:141-143`), and the two multi-seat practices already granted
(one at 5 seats, one at 11) received **$10 each**, measured this session.

⚠️ **A retroactive top-up to seat parity would therefore be a NEW ruled
mutation** — its own population re-derived at execution time, its own §2.5
declaration committed BEFORE the act, its own abort guards proved. It is not a
side effect of this ruling, and the billing session must not read it as one.

### ⚠️ The cap is a proposal, and it is written down as one

*"CAPPED (proposal: 10 seats)"* — the owner's own qualifier, kept verbatim so
the billing session inherits an **open question** rather than a silent default.
A cap that arrives as an unmarked constant is a decision nobody made.

### What the billing session still needs before it can start

- **ADMIN-1**, for what a seat IS inside a practice.
- **Class (d), the owner's alone:** Stripe keys, and flipping
  `BILLING_ENFORCED` — which converts a wired no-op into a gate that can refuse
  service.
- The cap, ruled rather than proposed.
