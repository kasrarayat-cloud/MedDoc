## #178 — THE MARGIN MULTIPLIER IS A CONFIGURABLE SETTING, NEVER A CONSTANT

**OWNER RULING, 2026-09-04. STANDING. An ADDENDUM to #177 (the pricing law).**
Recorded beside the pricing-law row; **the build lands inside the ADMIN arc.**

### The model, as ruled

| | ruled |
|---|---|
| **shape** | a **global default** (1.5 initially) **plus an optional per-practice override** |
| **who edits** | `SUPER_ADMIN`, in ADMIN |
| **audit** | **every** change — actor, timestamp, old → new, optional reason |
| **stamp** | every metered charge records the multiplier **in effect at billing time** on its own ledger line |
| **direction** | **forward only** — past bills are never rewritten |
| **validation** | bounds **≥ 1.0, ≤ 5.0**, two decimals |
| **effect** | at the **next metering cycle** |
| **visibility** | the ADMIN money view shows **"rate in effect" per practice** |

### ⚠️ THIS SHAPE ALREADY EXISTS IN THE SCHEMA — BUILD ON IT, DO NOT INVENT IT

Three pieces of prior art were measured before this was written down, and the
build should reuse all three rather than re-deriving them:

1. **`PriceRate` already does effective-dated, insert-never-update rate
   history.** Its own doc comment says it CLOSES the current row (`effectiveTo`)
   and **INSERTS** a new one, and that *"is what makes the history stable, and it
   is the property B3's gate proves."* That is precisely the forward-only
   property this ruling asks for, already built and already gated.
2. **The per-line stamp already has a home.** `ledger_entries.pricing` is a
   nullable `jsonb`. Measured in production: it is **NULL on all 177 rows** —
   because only grants exist and nothing has ever been metered. It is a stamp
   slot with no writer yet, not a column that needs adding.
3. **"Never back-rewrite" is already the codebase's stated law for rates.**
   `schema.prisma:2769` — *"Cost is computed at log time using `PRICING`
   constants … so historical rows preserve the rate that was charged at the time
   of the call. Update PRICING when providers change pricing — **never
   back-rewrite these rows**."* This ruling extends that same principle from the
   PROVIDER rate to the MARGIN multiplier.

⚠️ **AND THE METER DOES NOT READ `PriceRate` YET.** Its comment is explicit:
*"NOTHING IS BILLED FROM THIS TABLE YET … repointing it is B4/B6."* So the
multiplier's read path lands with, or after, that repoint — not before it, or the
stamp records a number nothing charged.

### The two failure modes this ruling forecloses, named so a build cannot miss them

- **A constant.** A multiplier compiled in is a rate nobody can change without a
  deploy, and — worse — a rate with no audit row saying who changed it.
- **A live lookup at read time.** If a bill is rendered by looking up *today's*
  multiplier, then changing the rate silently rewrites every past invoice. The
  stamp is what makes that impossible: **the ledger line carries the rate it was
  charged at**, so a rate change cannot reach backwards.

⚠️ **A MISSING RATE MUST BE A REFUSAL, NEVER A ZERO.** DISCOVERY §D.3 already
names this defect in the existing meter: `claudeCostCents` returns **0** for an
unknown model, so an unpriced model bills nothing instead of erroring. A missing
multiplier must not inherit that shape — it fails closed and refuses, or an
unconfigured practice silently bills at cost.

### Split of ownership

The **surface** — the ADMIN money view, the editor, the audit rows, the
"rate in effect" column — is **Design/Admin, inside the ADMIN arc**, and is
carried by the ADMIN-4 row added with this ruling.

The **metering read path and the stamp write** belong to the **billing session**,
which stays PARKED behind *ADMIN lands*. Neither half is useful alone: an editor
with no stamp writes a setting nothing honours, and a stamp with no editor
records a constant.

## #179 — ROS AT SYMPTOM GRANULARITY: a closed vocabulary, and no text matching anywhere

**OWNER-RULING. STANDING.** Parts 1–2 ratified as built; 3–7 in dependency order.

⚠️ **PROVENANCE, STATED FIRST SO THIS IS NOT READ AS MORE THAN IT IS.** This
body is written by the **implementing** session, from the ruling as received and
from the code that implements it — **not** transcribed verbatim from the war
room. It is recorded late: the standing rule is that the receiving session writes
the row **in its first commit, before building anything that depends on it**, and
that did not happen here. The gap is named rather than smoothed over, because a
ruling reconstructed after the build is exactly the artifact the rule exists to
prevent. **Where the wording below differs from the owner's, the owner's governs.**

### THE PROBLEM

The projector slugged L3's **free-text** `finding` into a concept, so the concept
space was whatever the model happened to say. Two consequences, both measured on
shipped code:

- **ONE SYMPTOM TICKED EVERY BOX.** Every ROS field carried the same
  `ros.<system>` concept, and `field-value-derivation`'s checkbox arm reads ONLY
  `fact.polarity` — the finding is discarded. A doctor saying *"reports
  heartburn"* affirmed heartburn, nausea, dysphagia and every other clause in
  that system alike.
- **TWO SYMPTOMS REFUSED THE DOCUMENT.** `ros` is not in
  `ACCUMULATING_NARRATIVE_CONCEPTS`, so a second affirmed finding became
  `multiple_distinct_supported_values` and the export conflicted.

Both are one root: **the concept could not ADDRESS the clause.**

### THE PARTS, as built

| part | what it does | where |
|---|---|---|
| **1** | A **closed ROS lexicon** — 13 systems, 72 addressable symptoms, plus `other`. ONE definition, two consumers: L3's structured-output schema and the projector both read it, so they cannot drift. | `template-twin/ros-lexicon.ts` |
| **1** | The **schema enforces it**: `system` is an enum, and a `superRefine` requires the symptom to belong to its own system. The model picks from a list rather than inventing one. | `worker/layers/03-extract-entities.ts` |
| **2** | The concept becomes **`ros.<system>.<symptom>`**, so a clause can address exactly what it covers. | `template-twin/encounter-facts/index.ts` |
| **2** | The registry pattern requires **three parts**. ⚠️ The two-part form is now REFUSED, deliberately: keeping `ros.<system>` representable is the defect. | `template-twin/concept-registry.ts` |
| **3** | **`conceptScope`** on `SemanticMapping` — the set of concepts a field's clause actually covers — with set-membership checked before anything else. | `template-twin/ir.ts`, `template-twin/validation/index.ts` |
| **5** | The **checkbox arm refuses a multi-concept scope**: a tick that would answer for more than one symptom is not written. | `template-twin/field-value-derivation.ts` |
| **7** | Temperature stripping moves to an **exact per-family decision table** with an explicit entry for each family, and an `UnknownTemperaturePolicyError` for anything unlisted — fail-closed rather than a silent default. | `packages/ai/src/anthropic.ts` |

### ⚠️ CORRECTION, 2026-09-05 — THE PART NUMBERING WAS WRONG IN THIS FILE

**Owner correction, applied from the ruling itself rather than re-derived.**

This table originally labelled the checkbox arm **part 4**. It is **part 5**,
and **there is no part 4** — the ruling has no such part. The superseded
wording is named here rather than quietly overwritten, because in this
programme the correction is the point.

⚠️ **AND NOTHING IS INVENTED TO FILL THE GAP.** Parts **4** and **6** are not
described here because this session was not given their content. An empty row
is honest; a plausible one written to make the table look complete would be a
fabrication wearing a ledger's authority — and the next session cannot tell the
two apart. If a part 4 is later found to exist, it is added then, dated.

**Why it mattered enough to fix:** the parts are stated to be *in dependency

### `other` IS ADMITTED AND DELIBERATELY UNADDRESSABLE

A symptom outside the list must **not** be silently dropped — that loses a
doctor's finding — and must **not** match a specific clause — that asserts
something the clause does not cover. `ros.<system>.other` therefore exists,
carries its evidence, and is excluded from every declared scope by construction.

### CONSEQUENCES MEASURED WHILE MOVING THE FIXTURES

Recorded here because they are properties of the ruling, not of the tests:

- **A mixed field's affirmed and denied facts now share a VALUE by
  construction.** They must share a concept to reach one field, and `value` IS
  the symptom token. The old ability to observe *"the denied value leaked into
  the document"* separately from *"the affirmed value printed"* is therefore
  **genuinely lost**. The evidence QUOTE remains as discriminator.
- **`multiple_distinct_supported_values` is now unreachable for ROS**, because
  two affirmed symptoms address two different clauses instead of colliding on
  one field. That is the ruling working as intended — it is the second bullet of
  THE PROBLEM above — but it retires any arm whose baseline was that conflict.
- **A field that used to BLOCK now renders blank.** Both halves of gate-157b's
  never-better-than-affirmed-alone arm sit on a raised floor: blank and
  non-blocking rather than blocked. That is #157(d) arriving — one negative
  sentence no longer costs the whole document.

## #180 — THE ALLOWLIST EXIT'S REASON SPLITS IN TWO

**Class (a) — a product decision with no ruled precedent. Owner-ruled 2026-09-04.**
Arrived as a board filing for the Data/Audit session, out of finding 8 of PR #951.

**THE QUESTION.** #951's adversarial pass established that the previous session's
own claim — that renaming the drop-reason token *"would merge a header refusal
with a fabrication refusal, which #149(b) forbids"* — was **false on both
halves**. Measured against shipped code: `ICD_DROP_REASONS` holds four tokens,
one per exit, and a header (`M54.5`) and a fabrication (`K58.3`) **already share**
`not_in_verified_allowlist`, because both leave through the same exit
(`isValidIcd10` failing). A rename merges nothing. And #149(b) is scoped to the
four EXITS — its cited precedent is five exits collapsing into one bucket — while
#149(e) explicitly *permits* the re-reading. So the split was **UNDECIDED, not
forbidden**, which is class (a) and reached the owner.

**RULED: THE TOKEN SPLITS.** A header refusal and a fabrication refusal are
different things to tell a doctor. One is ACTIONABLE — bill a billable child, and
one always exists, now provably (0 of 23,467 FY2026 headers have zero billable
descendants) — the other has nothing to offer.

Two reason tokens:

| token | case | carries |
|---|---|---|
| `header_use_billable_child` | a real ICD-10-CM entry that is not valid for submission | the enumerated children from `billableDescendantsOf` |
| `not_in_verified_allowlist` | a string that is not an ICD-10-CM code in any form | nothing — there is nothing to offer |

**SAME EXIT under #149(b)** — the four exits are unchanged — **a sub-reason within
it as #149(e) permits.** The new token gets its **audit label in the next enum
batch**; no `AuditAction` enum value is added with the token.

**SURFACE IS FILED SEPARATELY.** The Coding tab's rendering of the header case
(*"not billable as written — use one of: …"*, and the substitute chip parked under
#148) is **Design/Admin's** surface and is filed to them with this ruling.
**Data/Audit ships the token, the children, and the gate.**

**BUILT:** `feat/r180-token-split`, stacked on #951 → #946. 11 new gate assertions,
the 43 in `gate-f8-icd-drop-record` re-expressed rather than relaxed, 7 of 7
mutation arms proved.

⚠️ **FILED, NOT SOLVED — the stored children are a WRITE-TIME SNAPSHOT of an ICD
edition.** FY2027 takes effect **2026-10-01**, so a record written today can
outlive the edition that produced it. A reader that can reach
`billableDescendantsOf` should prefer a fresh derivation from `code`. Whether the
record should carry an edition stamp is not decided here.
