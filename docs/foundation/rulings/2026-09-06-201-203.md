## #201 — OWNER-RULING — `compilerVersion` BUMPS, AND THE ACTIVE COMPILED VERSIONS GET A RULED RECOMPILE

**STANDING.** REVIEW-DEFAULTS cannot fire in production, and the cause is not a
code defect. Measured 2026-09-06 against the production database:

    total_fields=185   scaffolded_true=0   with_scaffoldText=0     (4 compiled versions)

`scaffoldDefaultOfferable` refuses at `field.scaffolded !== true`, so **zero
production fields reach any of the REVIEW-DEFAULTS code** — item 1 (PR #1015,
already merged) included. `isScaffolded` landed **2026-09-05** in `255cd239`;
production's newest compiled version is **2026-09-03**. All four predate the
compiler that sets the flag, and nothing backfills it.

⚠️ **AND NOTHING COULD TELL THE TWO COMPILERS APART.** All four rows read
`compilerVersion = template-docx-compiler/1.0.0` — the string did not move when
`isScaffolded` landed, so a recompile sweep had no signal for *"was this produced
by a compiler that sets `scaffolded`"*. **That is the half this ruling fixes
first:** the version bumps, so the question becomes answerable, and only then does
the recompile have a defensible target set.

**THE ARM THIS RULING REQUIRES, AND IT IS THE WHOLE RISK:** `isScaffolded` is
**outside both hashes**. A recompile of an active, certified version must
therefore move **no** certification hash — not `structureSha256`, not
`templateTwinMappingsSha256`, not `approvedMappingsSha256`. This programme has
already measured a moved structure hash orphaning every certified twin, 10 of 10.
So the recompile lands with an arm asserting the certification hashes are
byte-identical across it, and a recompile that moves one is a FINDING, not a
migration note.

**The owner's 53-control form compiles fresh regardless** and does not wait on
this.

## #202 — OWNER-RULING — A PER-FIELD POLICY TOGGLE MUST NOT DE-CERTIFY A TEMPLATE

**STANDING. The current behaviour is the DEFECT, not the design.**

Measured at `certification-lifecycle.ts:552-561`: a mapping update drops the
compiled version's `certificationStatus` to `NEEDS_CONFIRMATION` and nulls
`latestSyntheticTestManifest` together with four `latestTest*` columns. So a
doctor ticking **"Expected blank — do not ask me about this"** on ONE field
destroys their template's synthetic proof and de-certifies the whole template.

**THE RULE:** a per-field policy toggle triggers **AUTOMATIC RE-CERTIFICATION** —
the self-test re-runs and the attestation re-issues. `NEEDS_CONFIRMATION` is for
when a **new human confirmation is actually required**, and a preference toggle
is not that. **Nulling the synthetic-test columns on a toggle is the defect to
fix**, not a cost to document.

⚠️ **THE DISTINCTION THAT MUST SURVIVE THE FIX:** re-certification is not the
same act as confirmation. The first is the machine re-proving what it already
attested under a changed input; the second is a human asserting something the
machine cannot. Collapsing them in either direction is how a certificate starts
attesting to behaviour nobody saw — which is the reason the hash moves at all.

## #203 — OWNER-RULING — `KEY_VERSION` v6 → v7 LANDS WITH THE #1018 FIX

**STANDING.** `insertableDefaults` lives **inside** the cached payload
(`CachedFill`, TTL 30 minutes). The #1018 fix changes **which fields that list
contains** without changing its **shape**, so a warm entry serves the **pre-fix
offer list** — the one that offers on every omit field — for up to the TTL after
deploy.

`fill-cache.ts:111` records the identical trap from the `v5 → v6` bump in its own
words: *"REVIEW-DEFAULTS widened `CachedFill` with `insertableDefaults` … Found by
an adversarial pass; **the shape changed and the key did not**."*

**This is that, one step subtler: the CONTENTS changed and the key did not.** The
file documents this class three times; this would have been the fourth. The bump
lands in the same commit as the fix, and the file's own design makes the writer
and the invalidation scan move together by construction.
