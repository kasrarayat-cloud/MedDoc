# RULING #198 — A MIGRATION-CARRYING DEPLOY REQUIRES THE STRICT DECLARATION

**Owner ruling, 2026-09-05. RENUMBERED from #188 on 2026-09-06 — see below.**

## THE RULING

A migration is **irreversible**, so its declaration must be **COMMITTED BEFORE
THE ACT** — the mutation-gate standard. Code-only deploys keep the ancestor
carry-forward path: **strictness is proportional to reversibility**, so #96(b)
is applied one level finer rather than overturned.

⚠️ **SPECIMEN.** Five August declarations were committed *after* their act began,
**two of them after an irreversible migration had already FINISHED** (+4m42s,
+5m46s). The gate accepted all five correctly by its own rules — which is the
finding. Evidence recoverable, gate not.

## ⚠️ WHY THE NUMBER MOVED, AND WHY THAT IS THE INTERESTING PART

**This ruling was recorded as #188. So was T4's** — *"the five clipboard formats
survive, the safety caption stays"* — and **T4's is the one that reached `main`.**
Both lanes claimed the same number on the same day, each correctly following the
protocol of claiming at record time, because **the protocol reads a file that
neither lane could see the other editing.**

The collision is not a typo. It is what a claim-at-record-time rule does when two
sessions record concurrently against branches, and it is invisible on each branch
individually — the shape a per-branch invariant cannot catch, because the
conflict exists only in the union.

⚠️ **AND IT HAD ALREADY HAPPENED FIVE TIMES BEFORE ANYBODY NOTICED.** Measured on
`main`: **#106, #109, #115, #116 and #131 each carry two rows.** This one was
caught only because a live citation started pointing at the wrong ruling.

## ⚠️ THE FULL REASONING AND THE SPECIMEN, CARRIED HERE 2026-09-06

**Appended, not rewritten.** This ruling was recorded twice — once in the batch
file that PR #990 carried — which stayed open — and once here,
when the renumber landed ahead of it via PR #1012. The version above is the
condensed one that reached `main` first. **The batch file's fuller statement is
carried here verbatim so that closing that PR loses nothing**, and the batch
file now records #189 and #190 alone.

**Answers the question the August retrospective raised, and answers it by
splitting the gate rather than tightening it everywhere.**

> **If the deploy's range contains a migration: `strict` — the declaration must
> be TRACKED, UNMODIFIED and COMMITTED before the act.**
> **If it does not: `present`, with the ancestor carry-forward path unchanged.**

**The reasoning is #96(b)'s own, applied one level finer.** Strictness is
proportional to reversibility. A code-only deploy is answerable by an image
rollback, so requiring a prior commit there would refuse every deploy whose
author lands the declaration in the same PR — a real habit, and halting the
programme to fix the weaker case. **A migration is not answerable by a
rollback.** It is the same irreversibility that already made
`run-ruled-mutation.sh` strict, so it takes the same standard.

### The specimen, and it is why this is a rule and not a preference

| | migration finished | declaration committed | gap |
|---|---|---|---|
| `079b9205` | 2026-08-09 00:01:00 | 00:05:42 | **+4m42s** |
| `50b02832` | 2026-08-11 09:06:35 | 09:12:21 | **+5m46s** |

In both, the irreversible act had **already completed** when the declaration
landed — so the record cannot distinguish an honest declaration from one
composed once the outcome was known, which is the entire product §2.5 buys.
Three further August declarations were committed after their deploy STARTED but
before the numbers existed: late, not tainted, and recorded as the lesser thing.

⚠️ **The gate accepted all five, correctly, by its own rules.** That is the
finding. Nobody bypassed anything.
