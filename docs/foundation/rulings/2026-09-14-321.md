# Ruling #321 — 2026-09-14 (the materialised fill-line is the field's BLANK STATE)

Recorded by the receiving session in its first commit, before building.

## #321 — OWNER-RULING — a materialised fill-line is shown when BLANK, replaced by the value when FILLED, never both; the 19-control count stands

**STANDING.** #320 shipped with an ACCEPTED cosmetic: because S2 materialises the
fill affordance as an underscore run ON THE LABEL ("PATIENT NAME: ______") and S1
inserts the control AFTER it, a filled auto-derived twin showed **both** —
"PATIENT NAME: ______John". The owner REVERSES that acceptance:

> a materialised line is shown when the field is BLANK and replaced by the value
> when filled — never both. The 19-control count stands.

### What it means, and why it is safe

The materialised line moves OFF the label and INTO the control's content. The
renderer clears/fills a control by **replacing its whole `w:sdtContent` subtree**
(certification-lifecycle.ts, the #164 fix — it used to clear only `w:t` nodes),
so a filled control shows the value alone and an unfilled one still shows the
line. This is the SAME shape the hand-built twins already use — the #317
colon-operative-note and the integration fixtures write "LABEL: " + a control
whose content is replaced on fill, never a standalone run beside it. Underscores
are FURNITURE, not a dictated value (#316), so a blank field showing the line is
a blank, not an undictated default.

### Scope

**S2 ONLY** — the twin S2 SYNTHESISED from a PDF, where the underscores are
materialised (not original bytes). An S1 doctor-uploaded DOCX prose form whose
underscores are the doctor's OWN bytes is byte-preserved by `deriveProseTwin`
invariant #1 and is NOT touched by this ruling ("materialised" is the operative
word). If the owner later wants the same for doctor-drawn DOCX lines, that is a
separate byte-preservation trade-off.

**The 19-control count stands** — this changes only WHERE the line lives, never
which fields are derived (#320's union rule is unchanged).

### Build

`pdf-form/fill-line-blank-state.ts` `relocateFillLinesToBlankState`: strips the
materialised underscore run from each label run immediately before a control, and
replaces that control's blank content ("Enter …") with the fill line. Self-
verifying via the caller's keystone (re-compile → same controls) and fail-safe
(an unrecognised shape returns null → the untransformed twin is kept). Wired into
`create-draft.ts` on the `wasPdf` (S2) path only, after `deriveProseTwin`. Own
adversarial pass.
