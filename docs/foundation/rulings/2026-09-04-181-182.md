## #181 — SIGN-OUT FAILS CLOSED

**THE MECHANISM**, read first-hand in `node_modules`. `events.signOut` holds
BOTH the `revokeSession` call AND the LOGOUT audit row, and
`@auth/core/lib/index.js` reaches it only through `actions.signOut`, which runs
strictly after `validateCSRF`. A failed CSRF check therefore skipped the revoke
and the audit row **together**: the session stayed live for the remaining 7 days
of the JWT's `maxAge` and the incident left no artefact anywhere. The 200 comes
from the client always sending `X-Auth-Return-Redirect`, which makes the error
path answer `Response.json({url})` — no cookies. The trigger needs no race:
`getCsrfToken()` ends `return response?.csrfToken ?? ""`.

**(a)/(b)** every client door goes through a server action, which revokes
in-process — no CSRF token to lose, no 200 that means nothing.
**(c)** a sign-in whose `UserSession` insert fails REFUSES. The line that died
promised login would succeed when session tracking did not, minting a token with
no `sessionId` — and every revocation gate lives behind `if (sessionId)`.
**(d)** a `validateSession` throw is INVALID, not a pass-through.
**(e)** a token with no `sessionId` is rejected.

## #182 — AMENDING #181(d)

⚠️ **#181(d) FIXED ONE END AND BROKE THE OTHER.** Returning `null` on a throw
made `@auth/core` call `sessionStore.clean()`, so a transient pool timeout
DELETED the cookie and ejected a working doctor permanently.

**(1)** A THROW is "cannot tell": the token is RETAINED and MARKED, the request
refused, the cookie kept so the next request re-validates. A DEFINITIVE answer
invalidates and clears. This also settles the reserved `isActive` fail-open in
`lib/auth.ts`, whose own comment had recorded the trade as pending.
**(2)** Sign-out reports success only on CONFIRMED revocation; an unresolvable
session id is a failure, not a silent skip; the cookie is NOT cleared on
failure, because a cleared cookie over a live server session is the lie; a
LOGOUT audit row is written on EVERY attempt with its outcome.
**(3)** Doors are ENUMERATED FROM THE TREE. The hand-written list was four of
six and green while `command-palette` — mounted in the root layout — discarded
the result on every page.
**(4)** A refused sign-in says session tracking failed, costs no rate-limit
strike, and does not consume an MFA recovery code.
**(5)** Arms assert RETURNS, not log text.

**ROUND THREE** added: consumers enumerated from the tree across all apps; the
middleware surfaces the refusal rather than redirecting to `/login`; and a
positive control that the product is not signed out.

## ⚠️ TWO KNOWN GAPS IN THE SHIPPED IMPLEMENTATION, RECORDED HERE RATHER THAN DISCOVERED LATER

**1 · THE "503" IS DECLARED AND NEVER EMITTED.**
`SessionUnverifiableError` carries `readonly status = 503`, and three comments
say the request is "REFUSED (503)". **Nothing maps it to an HTTP 503 response.**
The throw reaches the Next error boundary, which renders the verifying-session
surface — correct in substance (no PHI served, cookie kept, "you have not been
signed out", a retry) but **not the status code the ruling names**. Found by an
adversarial verification lens re-reading the author's own prose against the code.
**Filed as a follow-up; the comments must not keep asserting a status the system
does not send.**

**2 · A FAILED SIGN-OUT IS AUDITED AS `success = true`.**
`recordLogoutAttempt` never passes `success`, and `logAudit` applies
`success: input.success ?? true`. So the FAILED outcome is recorded in
`metadata.outcome` while the row's own success column says the opposite.
Strictly better than before — a failed sign-out previously left **no row at
all** — but a row that contradicts itself is a poor artefact. **Filed as a
follow-up.**
