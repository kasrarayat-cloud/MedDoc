## #247 — OWNER-RULING — **FAMILY 3 IS A NEW FACT CLASS, NOT A REUSE**

**STANDING.**

> **`sourceType` gains `'visit_record'`** — its own resolution status, its own
> validator arm, its own renderer allow-list entry, its own count bucket — and
> **every record-derived value carries it.**

**`withProcedureDateFact` MOVES ONTO IT AND STOPS CLAIMING
`encounter_evidence`.** That is not a tidy-up: today it injects the visit date
as a synthetic fact stamped `encounter_evidence`, so the frozen manifest records
a record value **as dictated**. It is the exact defect this class exists to
prevent, already shipped, and the class is not credible while its one precedent
keeps lying.

**It is PER-VISIT BY CONSTRUCTION.** `approved_practice_default` is
practice-wide and **stays refused**; a patient's name is not a property of a
practice.

> **PROVENANCE IS THE WHOLE POINT OF THE CLASS. The manifest says
> *"from the patient record."*** A fill path built on cited evidence must not
> let a record value borrow the doctor's voice.

### THE THREE MEMBERS, DECIDED INDIVIDUALLY

| member | decision |
|---|---|
| **patient name** and **age** | **TWO SEPARATE CONTROLS.** ⚠️ Acceptance row 3 is **four controls, not interpolation** — interpolation does not exist in this product and **will not be invented** for it. **Age is computed from the record's DOB at the visit date**, and is a **number**. |
| **referring physician** | **DICTATED ONLY.** An L3 field emitting concept `visit_metadata.referring_physician` with sourceType **`extraction`** — it is not record-derived and must not wear the new class. `classifyFieldSource` **stops pinning `/referring physician/` to `manual`**, and must also recognise **"Referring MD"**, the owner's actual label. |

### PHI — RULED, BECAUSE IT WAS ASKED

**A patient name in the VISIT-TIME fill manifest is the visit's own PHI, under
the same posture as the note it fills. Permitted there.**

**The CERTIFICATION artifact never contains a real name.** The existing
synthetic-evidence gate stays, **and gains an arm that a `visit_record` fact can
never reach a certification manifest.** The two artifacts have different
lifetimes and different audiences, and the rule follows the artifact rather than
the field.

### THE TWO CONSERVATIVE CALLS, RULED

1. **A `visit_metadata` mapping NEVER auto-confirms.** A control that prints a
   patient's name requires a human to have seen it.
2. **No fourth confirm act.** The existing confirm carries it, with the
   provenance shown — *"from the patient record."*

## STAGE B — WHAT WAS BUILT, AND THE ONE CALL THAT WAS NOT QUOTED

**Recorded 2026-09-07, after Stage A (the class) was ratified.** Stage A gave
`sourceType` its new member and moved `withProcedureDateFact` onto it. Stage B is
everything else the ruling names, and it is recorded here rather than only in a
commit message because two of its decisions are the ruling's own words being
applied to a case the ruling did not enumerate.

### THE RULED ITEMS, AND WHERE THEY LANDED

| ruled | landed |
|---|---|
| three `visit_metadata.*` registry entries | `REGISTRY_CONCEPTS`, as NAMES — never a `^visit_metadata\.` pattern, which would admit `.ssn` / `.mrn` / `.address` the day somebody typed one |
| `classifyFieldSource` un-pinned, and recognising **"Referring MD"** | `MANUAL_LABEL_PATTERNS` loses `/referring\s+physician/i`; the label pins the CONCEPT instead |
| the dictated `referring_physician` L3 field + prompt + projector | `03-extract-entities.ts`, `liftStringToFact('name')`; projector emits `encounter_evidence` |
| `withVisitMetadataFacts` (name; DOB-derived age at the visit date) | `visit-metadata.ts` — new module, mirroring `procedure-date.ts` |
| the visit record through the five fill call sites | **loaded once in the shared reader**, not threaded five times — see below |
| the `visit_record` resolution status, validator arm, renderer allow-list, count bucket | `record_derived`, promoted at ONE point inside `makeResolution` |
| (1) a `visit_metadata` mapping never auto-confirms | `decideAutoConfirm` refuses it FIRST, before any confirming arm |
| (2) no fourth confirm act | it stays in the ordinary `confirm` class, with the provenance rendered on the row |

### ⚠️ THE FIVE CALL SITES BECAME ONE READ, AND THAT IS THE RULING HONOURED RATHER THAN NARROWED

The ruling says *"the visit record threaded through fill-engine's five call
sites, the four that don't load the patient today included."* All five funnel
through `readAndPrepareTemplateTwinFill`, which already loads the clinician's
overrides for exactly this reason, and says so in its own header:

> *"the behaviour lives on the shared function, not on four caller-side
> checklists that are kept complete by hand."*

So the patient is loaded there — two columns, practice-scoped in the `where` —
and every one of the five carries it by construction. A parameter threaded five
times would have made *"did you remember the patient record?"* a per-caller
habit, on the one control that prints a patient's name. Declared in
`gate-practice-scope.test.ts`'s system allowlist, 2 → 3, with the select named.

### ⚠️ THE CALL THAT WAS NOT QUOTED: **BULK CONFIRM DOES NOT SWEEP THESE ROWS**

The ruling states (1) never auto-confirm and (2) no fourth act. It does not name
the **"Confirm all N proposed"** button, which sits between them — and that
button is a HUMAN act that certifies every row of the class at once, including
rows below the fold of a scrolling list.

**Read against (1)'s stated REASON — *"a control that prints a patient's name
requires a human to have seen it"* — the bulk sweep defeats it through a
different door.** So `bulkConfirmable()` excludes `sourceType: 'visit_metadata'`
while `confirmClassOf()` keeps it in the ordinary `confirm` class: same button,
same picker, same writer, same code path, nothing new to learn. It is simply not
included in a shortcut whose entire purpose is not reading the rows. The cost is
one click, on the one or two controls that print a patient's identity.

⚠️ **THIS IS A CALL, NOT A QUOTE, AND IT IS THE OWNER'S TO OVERRULE.** It is one
predicate in one file (`native-template-manager.tsx`) with its own arm, so
reversing it is a two-line change.

### THE OTHER TWO DECISIONS WORTH THE OWNER'S EYE

**1 · ON WM_IOV THE REFERRING CONTROL BECOMES `verified_note_selection`, NOT
`extraction`.** The ruling says the referrer is `extraction`; that is what
happens on the owner's GI letter, where the control is free text. On the
ultrasound form the same label is an ENUMERATED dropdown of the practice's own
referrers, so `classifyFieldSource`'s enumerated arm claims it and the doctor's
adopted pick answers it. The CONCEPT is identical on both — a field's source
depends on the shape the form gave it; its meaning does not. Consequence,
recorded: **F24's residual set moved from 5 to 4 and the census closes at 76 of
80** (ruling #147(2)'s set-equality clause caught it; RELAY updated).

**2 · THE RESOLVER'S EXPERIENCER GATE WAS WIDENED BY EXACTLY ONE CONCEPT.**
`experiencer` answers *who is this fact about*, and the referring clinician is
not the patient — so the projector emits `other`, and without a matching arm the
resolver refuses `experiencer_not_approved` on every visit that dictates a
referrer. The alternative was to stamp `patient` in the projector, which would
have made every test pass and written into the frozen manifest that a named
outside physician is the patient. That is the `encounter_evidence`
misattribution again, one field over.

### PHI

The certification artifact is guarded on BOTH sides now. Stage A's
`assertNoRecordDerivedFacts` read this function's INPUT; Stage B made injection
possible one layer BELOW that check, inside `prepareTemplateTwinFill`, so the
predicate is also driven over the produced **manifest's own fact list** — the
artifact the ruling names. Today both pass because the certification path
threads no patient record; the guard exists for the day somebody does.

## THE ADVERSARIAL PASS ON STAGE B — WHAT IT FOUND, AND WHAT IT COST

**Four lenses, in write-guarded sandboxes on the finished diff: provenance,
blanking, PHI/tenancy, stored-artifact.** Every finding below was demonstrated by
running the shipped chain with a concrete input, and every one was re-run here
before a line was changed. The suite was green over all of them — 452 files,
6268 tests — which is the whole argument for the pass existing.

### TWO WOULD HAVE PRINTED WRONG CONTENT ON A SIGNED DOCUMENT

| # | what | why it happened |
|---|---|---|
| 1 | a CHECKBOX labelled `Patient` is **TICKED because the chart has a name in it** | `classifyFieldSource` read the LABEL and not the KIND; the resolver's checkbox arm reads only polarity and DISCARDS the value. `record_derived / true`, valid, zero issues. **Canon 141.** |
| 2 | the referrer's NAME rendered into **`Referring Physician Fax` / `NPI` / `Address` / `Phone` / `signature`** | the new pattern was anchored at ONE end. A REGRESSION — those labels matched the old unanchored manual pattern and rendered an honest blank. And the same commit anchored the other two patterns at both ends, with a written argument about `Age of onset`. |

### TWO WOULD HAVE WITHHELD THE WHOLE DOCUMENT

| # | what | why it happened |
|---|---|---|
| 3 | *"Referred by Dr. Lee for **possible** inflammatory bowel disease"* → `uncertain` → `ambiguous` → `FIELD_AMBIGUOUS` → **blocking** → `render: null` | polarity was left to inference. The hedge is about the DIAGNOSIS. `clinicallyMaterial: true` is hard-coded at all twelve compiler emission sites, so that issue is unconditionally blocking. |
| 4 | a mapping with `approvedSynonyms` plus a dictated fact of the same value → one `supported` resolution citing BOTH → the new `SUPPORTED_STATUS_CITES_RECORD_EVIDENCE` arm refuses it | the injector's *"real evidence wins"* guard compared CONCEPT STRINGS while the resolver used `conceptMatches`. **Two guards, one relation, different answers.** |

### TWO WOULD HAVE BLANKED A CONTROL SILENTLY

- **The word "referred" stamps the fact `planned`.** `PLANNED` is
  `/plan|will|schedule|refer(red|ral)?|start|follow-up/`, so the very word that
  identifies a referral sentence sets its tense. Against a mapping declaring
  `current` — which the proposer invites the model to propose — that is
  `temporality_not_approved`: permanently blank, validation green. The frozen
  manifest also recorded a referral that HAPPENED as planned.
- **One fact per concept inherited only the FIRST mapping's tense.** Two
  controls on one concept with different declared tenses: the second came back
  blank, or blocking with `required: true`. The outcome depended on the ORDER of
  the mappings array.

### AND THREE CLAIMS OF MINE WERE FALSE

- *"an `extraction` mapping citing a record concept is permanently blank"* —
  **no.** The resolver never compares a mapping's `sourceType` to a fact's.
  Measured: a mis-proposed HPI mapping printed **the patient's name into a
  clinical narrative control**, `record_derived`, valid, zero issues. Prompt
  omission is a nudge; the gate is now `refuseRecordDerivedOnNonMetadata`.
- *"the select is guarded by the allowlist"* — **no.** The allowlist counts CALL
  SITES and cannot see a `select`; widening it to `mrn` or `problemList` left
  every gate green. It has its own arm now.
- *"compared on UTC calendar parts, so a server timezone cannot move a birthday"*
  — true of the DOB, false of the visit (`createdAt` is a `timestamptz`). An
  evening encounter west of UTC on the day before a birthday prints an age one
  year high. **Not fixed: a practice has no timezone column**, so the input to
  fix it with does not exist. Stated in the source rather than hidden.

### TWO FINDINGS THAT ARE NOT CODE

- **THE PATIENT RECORD WAS NOT IN THE MANIFEST FRESHNESS KEY.** Worker fills →
  front desk corrects a name → the doctor's preview RECOMPUTES and shows the
  correction → signing finds note and overrides unchanged, returns
  `already_fresh`, and freezes the OLD name. *The document reviewed is not the
  document signed.* Now compared by timestamp — conservative, no migration; a
  `patientSha256` column beside `overridesSha256` is what it should become.
- **`confirm-live-template-mappings.ts` WOULD SILENTLY REVERT THIS RULING.** A
  spent ruled-mutation script, run against production twice, whose PLAN still
  pins `Referring MD` / `Patient` / `Age` / `Total minutes` to `manual`/NULL. It
  is now REFUSED rather than corrected — a one-shot mutation whose act is done
  is history, and history that can still be executed is not history. ⚠️ **And
  this diff CITED that file as evidence for the owner's labels while it
  disagreed about the answer.** A file can be right about the question and wrong
  about the answer; quoting half of it is how that survives.

### WHAT THE PASS CONFIRMED RATHER THAN BROKE

The single promotion point in `makeResolution`; the counts-key sha stability
(canon 140) verified byte-identically in both directions; tenancy of the new
patient read (a composite FK makes a cross-practice patient unrepresentable);
the certification artifact having no second door; no PHI in any log, audit row,
error message or object key; and the `experiencer` widening having exactly one
producer and one concept.

### STANDING RESIDUALS, NAMED

- **THIS CHANGE IS A NO-OP ON THE OWNER'S LIVE CERTIFIED TEMPLATE** until the
  ruled re-upload → transfer → re-propose → confirm → certify → activate
  sequence runs. Certified mappings are immutable and the three controls are
  `manual`/NULL today. That is the ruling's own order, not a defect — recorded
  because the classifier narrative reads as though the field is now reached.
- **THE CHANGE IS FORWARD-ONLY.** A manifest written after it (`record_derived`,
  `counts.recordDerived`) does not parse under the previous schema. Survivable
  because nothing re-parses a real visit's stored manifest; stated so a rollback
  is not planned in ignorance.
- **`factId` is an unsalted, cross-tenant-stable digest**, and for
  `patient_age` the input domain is 131 values, so it is plaintext-equivalent.
  Not an egress route — it sits in the same JSON as the plaintext value — but it
  is a linkage key for anyone holding many manifests across tenants.
