## THE QUESTION, AND WHO ASKED IT

ADMIN-1 (PR #1004, merged `a3eab932`, live in production as of `832f8e81`)
shipped the members page **fail-closed on a question it could not answer**, and
said so in four places rather than guessing. `practice-admin.ts` put it plainly:

> *"⚠️ `OWNER` IS DELIBERATELY ABSENT, AND ITS ABSENCE IS AN OPEN QUESTION RATHER
> THAN A RULING. Whether one OWNER may create another — whether OWNER is
> exclusive at all — is a product decision with no ruled precedent … A refusal is
> recoverable by a ruling; an accidental second OWNER is somebody else's clinic."*

That is STANDING AUTHORITY class **(a)** — a product decision with no ruled
precedent — and it was correctly routed to the owner rather than decided below.

## THE RULING

**A practice may have more than one OWNER, and an existing OWNER may create
another** — by minting an OWNER seat, or by promoting an existing member.
`ASSIGNABLE_ROLES` widens from `['CLINICIAN','TECH']` to
`['OWNER','CLINICIAN','TECH']`.

**Demotion and removal of an OWNER stay refused, and the surface says so.**
`CANNOT_CHANGE_AN_OWNER` remains unconditional.

## ⚠️ THE FINDING THAT SHAPED THIS RULING — THE TWO GUARDS ARE INDEPENDENT

The obvious reading is that non-exclusivity destroys the *"every practice has at
least one OWNER"* invariant and therefore **forces** a last-owner guard. **That
reading is wrong, it was asserted by this session before it was checked, and an
adversarial verifier refuted it against the code.** Recorded here because it is
the exact misreading the next session will arrive with.

| side | where | what it does |
|---|---|---|
| **promotion** | `RoleSchema` → `z.enum(ASSIGNABLE_ROLES)`, `practice-roles.ts:51` | constrains what role may be **assigned** |
| **demotion** | `if (target.practiceRole === 'OWNER') → CANNOT_CHANGE_AN_OWNER`, `actions/practice-members.ts:180` | refuses changing an OWNER **unconditionally, whatever role is asked for** |

They are separate branches at different lines. Widening the first does **not**
reach the second, so the invariant continues to hold **STRUCTURALLY** — no
count, no read-then-write race — for precisely the reason ADMIN-1's author gave.

**So this ruling costs no concurrency work at all**, which is why it can ship on
its own.

⚠️ **AND THE INCIDENTAL ENFORCEMENT IS GONE, WHICH IS THE PART THAT NEEDED A NEW
PROOF ARM.** Before this change, *"you cannot demote an owner"* was **also**
enforced by accident: every reachable target role was `CLINICIAN` or `TECH`, so
`RoleSchema` rejected an OWNER→OWNER request before the guard was consulted. Now
`OWNER` is a legal target, and the explicit branch is the **only** thing left
standing between an owner and a role write. `gate-admin1-practice-admin` gains
an arm that asks for OWNER→OWNER specifically, because that is the one input
that isolates the guard from the schema.

## WHAT IS FILED, NOT FORGOTTEN — AND WHY IT IS ITS OWN ROW

**OWNER demotion and removal is NEEDED.** Partners leave practices; a build
where the only owner is permanent is a build that cannot survive a partnership
changing. It is filed as **ADMIN-5**, not deferred indefinitely.

It is a separate row because it is the half that requires a **last-owner
guard**, and the owner's direction on that guard is explicit:

> **It must be correct under concurrency — a partial unique index or a
> SERIALIZABLE transaction, never a count read and then acted on.**

⚠️ **THE FAILING SHAPE, NAMED SO IT IS NOT REBUILT:** two owners demoting each
other simultaneously. `SELECT count(*) WHERE practiceRole='OWNER'` returns 2 to
both transactions, both conclude *"there is another owner, this is safe"*, both
write, and the practice is left with **zero** owners and nobody able to
administer it. A read-then-act check cannot see that interleaving by
construction — it is not a matter of making the window smaller.

Two shapes that actually hold, either acceptable:

- a **partial unique index** that makes "the last owner" a constraint the
  database enforces, so the second writer fails rather than races;
- a **SERIALIZABLE** transaction, which makes the interleaving a serialization
  failure the application must retry — with the retry bounded, per ruling
  #187(a)'s lesson that a blanket catch around a `40001` signs the wrong thing.

## WHY NOT SHIP BOTH TOGETHER

*Two claims wearing one diff* — ruling #188's own words about the post-state
change. Promotion is a one-constant widening with no concurrency surface;
removal is a schema-or-isolation decision with an irreversible failure mode.
Bundling them would put a change that needs no proof of concurrency correctness
behind one that does.

## THE SURFACE STATES THE HALF THAT IS NOT BUILT

`members-owner-note`, rendered for administrators only:

> *"You can make another member an owner. Owners cannot be demoted or removed
> here yet — ask support if a partner is leaving the practice."*

⚠️ **A MISSING CONTROL READS AS AN OVERSIGHT.** Saying it tells the doctor the
refusal is deliberate and that there is a route today. This is the same posture
ADMIN-1 took with the fail-closed refusal, and the refusal MESSAGE is updated
for the same reason: it used to read *"who may promote and demote an owner is
not settled"*, which became false in the doctor's face the moment promotion
shipped. A gate arm now asserts that string is gone.

## A SECOND DEFECT THE CHANGE EXPOSED, FIXED IN THE SAME COMMIT

Both role selects **hardcoded** `CLINICIAN`/`TECH` instead of deriving from
`ASSIGNABLE_ROLES`. Widening the server constant would therefore have passed
every server test **while the page kept offering the old two** — the feature
shipping invisible under a fully green suite.

Both selects now derive from the constant, and the panel gate asserts against
the imported `ASSIGNABLE_ROLES` rather than a retyped literal, so the two cannot
disagree again.

⚠️ **AND THAT FIX HAD ITS OWN TRAP, WHICH IS WHY THE VOCABULARY MOVED FILES.**
`practice-admin.ts` imports `node:crypto`, Prisma and the audit logger; the
panel is `'use client'`. Importing the guard to reach the list would have pulled
the server graph into the client bundle. The vocabulary now lives in
`lib/practice-roles.ts` with **no runtime imports**, and `practice-admin.ts`
re-exports it so every existing import resolves unchanged.

⚠️ **AND THE RE-EXPORT ITSELF FAILED FIRST, SILENTLY TO `tsc`.** A bare
`export { PRACTICE_ADMIN_ROLE } from './practice-roles'` forwards the name to
importers and creates **no binding in the re-exporting module's own scope** —
so `requirePracticeAdmin`, which compares against it, threw
`PRACTICE_ADMIN_ROLE is not defined` **at runtime on the seat-handing surface**
while the typechecker and every importer stayed happy. It is imported *and*
re-exported now. The gate suite caught it; review would not have.

## PROOF

`gate-admin1-practice-admin` (28 arms) and `gate-admin1-members-panel` (10 arms)
— **38 passing**, `tsc --noEmit` clean.

What would make them fail, stated first, in each file's own header:
OWNER stops being assignable; the assignable enum stops constraining anything
(`SUPER_ADMIN`, `ADMIN`, `''` must still be refused — the non-vacuity control);
an OWNER becomes demotable; the OWNER→OWNER request stops being refused; a
select stops deriving from `ASSIGNABLE_ROLES`; the not-built half stops being
stated on the surface.
