# Rulings #219 – #224 — 2026-09-07

them**, per the standing rule that a ruling existing only in a session
transcript is not a ruling. Docs only.

Four of the six (#220, #221, #222, #223) govern work already in flight on

## #219 — OWNER-RULING — A NUMBER IS CLAIMED BY THE ROW THAT **LANDS** FIRST

**STANDING. PROTOCOL AMENDMENT.**

> **A branch is a claim. A merged row is a fact.**

The `#210` collision resolves for the **landed** claim: `#210` stays with
PR #1034, and the custom-file lane's entry renumbered to **#215–#218**.

### ⚠️ THE ARGUMENT IS THAT BOTH LANES BELIEVED THEY WERE FIRST

Measured, from the merged history:

| | authored | PR opened | PR merged |
|---|---|---|---|
| #1034 (this lane) | `03:19:31Z` | `03:20:19Z` | **`03:47:01Z`** |
| #1035 (custom-file) | `03:21:16Z` | `03:21:42Z` | `04:27:32Z` |

By commit time this lane was earlier **by 1 minute 45 seconds**. The other
lane's commit message states the peer *"claimed it 27 minutes later"* — which is
**their claim time measured against this lane's MERGE time**
(`03:21:16Z → 03:47:01Z ≈ 26 minutes`).

**Neither account is dishonest and neither could settle it.** Claim time is
computed from whatever each session can see, and what a session can see differs
by lane, by fetch time, and by whether the other side had pushed yet. **It is
unverifiable across lanes by construction.**

> **Landing order is ONE fact, in ONE place, that both parties read the same
> way.** That is the whole reason the rule moves to it.

### ⚠️ AND THE SECOND-ORDER TRAP, WHICH THE PEER HANDLED CORRECTLY

The owner's earlier instruction was *"the peer entry renumbers to #211"*. **That
instruction became unbuildable between being given and being executed**: #1034
had already merged `#210`–`#214` in one commit, so `#211` was now a different
ruling.

They named the deviation instead of absorbing it, and moved to the next free
block. **Two rulings sharing a number in permanent canon is not undoable;
renumbering an unmerged entry is one commit.** Recorded here because the
reasoning generalises: *when an instruction is overtaken by a landing, say so
and take the cheaper reversible path — do not execute it into a worse state.*

## #220 — OWNER-RULING — THE CONSTRAINT-TRIGGER DEPARTURE IS RATIFIED

**STANDING. Ratifies three closures the adversarial pass forced.**

### THE SHAPE

**Statement-end evaluation stands. The invariant is unchanged.**

#210's literal wording said *"a `BEFORE UPDATE/DELETE` trigger"*. The `BEFORE`
row form **refused the E2E suite's own teardown** (`tests/e2e/helpers/cleanup.ts:99`)
because a row trigger judges each row before the statement's other rows are
applied — and it did so **order-dependently**, which is worse than wrong. The
shape is now `AFTER … DEFERRABLE INITIALLY IMMEDIATE`.

**Per #200: a ruling binds the INVARIANT and its PROOF, never its MECHANISM.**

### THE ADVISORY LOCK STAYS — AND WHY THAT IS NOT CAUTION

Once `FOR UPDATE` landed on the sibling owner rows, the lock's **original**
control stopped discriminating: deleting the lock no longer broke the demotion
race.

⚠️ **A CONTROL THAT HAS STOPPED DISCRIMINATING MUST BE REPLACED, NOT QUIETLY
KEPT** (canon 121). The replacement fires:

> **suspend-a-solo-owner vs insert-a-member, same instant:
> 8 of 12 violations WITHOUT the advisory lock, 0 of 12 WITH it.**

The INSERT guard has no row to `FOR UPDATE`, so the shared lock is the only
thing making those two writes mutually exclusive. **The lock is kept because it
was proven load-bearing somewhere else, not because it was there already.**

### ALSO RATIFIED

- **REPEATABLE READ write skew** — the lock serialized correctly and the
  invariant broke anyway, because the second transaction's snapshot predated the
  first's commit. `FOR UPDATE` makes that case **raise** instead of skew.
- **Self-demotion** — exemption 2 now counts the row that **survives** an
  `UPDATE`. A solo owner demoting themselves is the person stranded.

## #221 — OWNER-RULING — ONE PREDICATE FOR "ABLE OWNER"

**STANDING.**

> **The trigger, the app-layer refusal, and #1026's guard all derive from a
> SINGLE CONSTANT: active, not deactivated, not suspended, able to sign in.**

### WHY A CONSTANT AND NOT THREE AGREEING COPIES

Three readers of one rule is the shape where changing one makes the system
contradict itself **while every arm stays green** — each arm points at one
reader, so nothing fails while they disagree.

### ⚠️ AND THE DIVERGENCE IS ALREADY IN PRODUCTION DATA

#1026's `LAST_OWNER_CLAUSE` counts `u2."deactivatedAt" IS NULL` alone. Measured
against production:

| | |
|---|---|
| OWNER rows that clause counts, **who cannot sign in** | **6** |
| practices where it disagrees with "can administer" | **6** |
| ⚠️ one of them | **11 members · `clause_sees = 2` · ONE able owner** |

So the guard believes there is a spare owner and **permits demoting the only
administrator**, leaving eleven people in a practice nobody can log in to run.

**#1026 adopts the shared constant when #212 lands.** This is filed to that PR
**as the ruling, not as a suggestion**.

⚠️ **THE FIX IS NEVER "ADD FOUR CONDITIONS TO THAT SUBQUERY".** That authors the
second copy — the exact thing this ruling exists to prevent.

## #222 — OWNER-RULING — THE SIX ZERO-OWNER PRACTICES, AND THE ARM THAT PROTECTS THEM

**STANDING.**

### THE ADMIN HALF

**Identify each of the six** — signup shell, abandoned, or test — and **assign an
owner or archive it.** This is a data-hygiene item for ADMIN.

### THE TRIGGER HALF, AND IT IS AN ARM

> **The trigger must never refuse a write that does not REDUCE an owner count
> from `≥1` to `0`. A zero-owner practice stays writable.**

The invariant is about the write that takes a practice from **one able owner to
none**. A practice already at zero **cannot be reduced by any write**, so
refusing there would be **a lockout created by the guard against lockout** — and
it would fall on six real practices holding seven real users.

Exemption 1 implements it. ⚠️ **Arming it is what keeps it true**, which is why
this is a ruling and not a comment.

### ⚠️ AND THE TWO HALVES DO NOT SWAP

**A guard must not silently repair the rows it guards.** The migration
deliberately does not "fix" the six — it records the count at install time and
leaves them writable. Rewriting user rows nobody asked it to touch is a
different act from refusing a bad write, and only one of them was ruled.

## #223 — OWNER-RULING — #1018 GETS A FIFTH ROUND; #1036 STAYS DRAFT

**STANDING.**

**#1018:** round four returned **24 verified, 20 surviving, 2 clinical-harm**.
Its fixes are themselves a finished diff, and a finished diff is refuted.

⚠️ **FIVE ROUNDS IS NOT PROCESS THEATRE.** Every round so far has found real
defects in a diff its author believed was finished — including round four's
finding that the **round-three fixes left every weak arm in place** while the
commit messages described the coverage as replaced. **The belief is not
evidence, and it has now been wrong four times on that branch.**

**#1036** is held to the same standard by the same sentence: **13 of 28 findings
open**, led by *nothing runs either proof in CI*.

> **A clean round is the condition. Not a count of rounds served.**

## #224 — OWNER-RULING — #214 IS NOT DISCHARGEABLE, AND DECLINING WAS CORRECT

**STANDING. Carries a canon entry.**

> **CANON: scratch is written only under the session sandbox; a file outside it
> has no reaper.**

`scripts/reap-session-scratch.sh` refuses everything outside `/tmp/claude-1000/`,
and `shred` is denied outright — ruling **#166**, because a permission entry is a
command-text **PREFIX** and no path scope is safe. **Both are correct.** Between
them, a bare `/tmp` file is **unreapable by any granted instrument**.

### ⚠️ THE CURE IS AT THE WRITE, NOT AT THE SWEEP

A file written outside the sandbox has no reaper **at the moment it is created**.
So the close-out obligation is discharged by **never creating it there** — not by
finding a stronger broom later.

**The seven bare-`/tmp` files are the OWNER's to remove.**

Moving them into the sandbox to make them destroyable is **refused**: it routes
around a deliberate deny while leaving an audit trail saying the door was used.
**Reporting the gap is the correct discharge; laundering past it is not.**
