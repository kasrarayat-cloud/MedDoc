## WHAT IS BEING DISCARDED, NAMED

Each merge lands a commit on `main`, and GitHub cancels `main`'s in-flight runs
when the next one lands. So merges two, three and four each destroy the
**merge-commit citation of the merge before them**.

**Those runs are MINE, all four of them.** No other actor is waiting on a
`main` run in this window — checked by both views immediately before the first
merge, and re-checked between merges.

⚠️ **AND THE DISCHARGE IS NAMED IN ADVANCE, BECAUSE A RECOVERY YOU CANNOT
SCHEDULE IS NOT A PLAN.** The FINAL merge commit's citation covers all four
PRs: it is a descendant of every one of them, so its four green runs certify
the tree that actually ships, not a parent of it. That is the
descendant-citation pattern used deliberately rather than as a recovery.

**The batch is not complete until that final commit is 4 of 4.** If it comes
back red, the batch has failed as a unit and the fix goes on top — no merge in
this batch is treated as discharged by its own cancelled run.

## THE PRE-MERGE CHECK THAT IS NOT WAIVED

`scripts/merge-pr.sh` is the only door; `gh pr merge` is denied. Each merge
re-reads the PR afterwards rather than trusting the exit code, because
`--delete-branch` is on record reporting one failure while silently leaving
another.

⚠️ **ALL FOUR PRs ARE DRAFTS.** Converting each to ready fires
`ready_for_review`, and `a11y.yml` is the only subscriber — measured, one line:

    grep -n "ready_for_review" .github/workflows/*.yml
    -> a11y.yml:45  types: [opened, synchronize, reopened, ready_for_review]

Each is converted to ready only once its own citation is COMPLETE, so the
event cancels nothing.

## ⚠️ AMENDED BEFORE THE FIRST MERGE — THE THIRD DOOR COSTS MORE THAN THIS DECLARATION SAID

**Written 2026-09-08 after the first `merge-pr.sh` attempt REFUSED, and before
any merge succeeded.** The act has not happened, so this is a correction to a
prediction rather than a story told about an outcome — the distinction §2.5
exists to protect.

**WHAT THIS DECLARATION GOT WRONG.** It said converting a draft to ready once
its citation is complete means *"the event cancels nothing"*. That is true and
it is not the whole cost.

> **`gh pr ready` does not only risk CANCELLING a run. It STARTS one — and if
> that workflow is a REQUIRED check, the PR is `BLOCKED` until the new run
> finishes, however complete the citation already was.**

**MEASURED ON #1055.** Citation complete at `00:19:34Z`, 4 of 4. `gh pr ready`
at `04:24:08Z` started a second `a11y-ci` on the same head. Nothing was
cancelled — the first had long finished. But `mergeStateStatus` went `BLOCKED`
and `merge-pr.sh` correctly refused to claim a merge it had not earned.

⚠️ **AND THE TELL WAS THE SAME ARITHMETIC AS THE ORIGINAL SIGHTING:** the
branch view showed **five runs for four workflows**, `a11y-ci` twice.
*Arithmetic that does not reconcile is a finding* — the second time that exact
count has caught this door.

**WHY THE CANON'S HABIT IS BETTER THAN WHAT THIS SESSION DID.** The recorded
advice is *"convert to ready BEFORE the push that carries the citation"*. This
session did the opposite deliberately, reasoning that a late conversion cannot
cancel a finished run. That reasoning is correct and it optimised the wrong
quantity: converting early means the push's own runs ARE the citation and no
second run is ever started. Converting late guarantees one extra required run
per PR — here, four of them.

**WHAT CHANGED IN THE PLAN, AND WHAT DID NOT.** The remaining three were
converted to ready IMMEDIATELY and in parallel, so their fresh `a11y-ci` runs
overlap instead of queueing behind four separate merges — one ~5 minute wait
for the batch rather than four. Each was checked for in-flight runs first and
all three showed **zero pending**, so nothing was cancelled by any conversion.

**The order, the discharge, and the fail-as-a-unit rule are unchanged.**
