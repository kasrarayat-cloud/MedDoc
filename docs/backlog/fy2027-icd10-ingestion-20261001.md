# BOARD ROW — FY2027 ICD-10-CM ingestion

# ⚠️ DATED: the codes change on **2026-10-01**, ready or not

**Filed 2026-09-04 by the Data/Audit session. 27 days of notice.**
**Status: NOT STARTED. The generator is parameterised and REFUSES fy2027 until pinned.**

CMS's FY2027 ICD-10-CM release takes effect **2026-10-01**. On that date every
code in `ICD10_ALLOWLIST` is an FY2026 code, and the set stops being the current
one. Nothing breaks loudly — the gates all stay green, because they assert
FY2026's counts against FY2026's data. **That is the hazard: the failure is a
silent staleness, not a red build.**

⚠️ **THE URL IS NOT DERIVABLE FROM THE YEAR, AND THIS WAS MEASURED, NOT ASSUMED.**

```
FY2026 tables:  2026-code-tables-tabular-and-index.zip   200
FY2027 tables:  2027-code-tables-tabular-index.zip       200    <- no "and-"
FY2027 tables:  2027-code-tables-tabular-and-index.zip   404
FY2026 tables:  2026-code-tables-tabular-index.zip       404
```

CMS dropped `and-` between the two years. A year-substituting helper would have
404'd in the year it mattered, so `EDITIONS` carries one literal URL per year.

## The cadence, recorded so nobody rediscovers it

- **October release** — effective Oct 1 – Sep 30, published ~June.
- **April 1 mid-year update** — effective Apr 1 – Sep 30, published ~December.

⚠️ The April 1 **2026** update carried **no code changes** — byte-identical
members, and its own addenda read *"0 additions, 0 deletions, 0 revisions."*
**That is a fact about FY2026, not a rule.** An April update can carry codes, and
the next one gets checked the same way rather than assumed empty.

## The work, in order

1. **Download** `2027-code-descriptions-tabular-order.zip`; record its sha256 and
   byte length, and the sha256 of `icd10cm_codes_2027.txt` and
   `icd10cm_order_2027.txt`.
2. **Read the expected counts out of the release's OWN addenda** — never carry
   FY2026's 74,719 / 23,467 forward. The generator refuses without them.
3. Fill `EDITIONS.fy2027` and run `--edition fy2027`. All 29 assertions must pass
   on FY2027's own numbers.
4. **Diff FY2026 → FY2027** and publish the delta: codes added, deleted, and —
   the one that matters — **codes that changed billable/header status**. A code
   that was billable and becomes a header is a code the floor must start
   refusing.
5. **Re-run the T8 partition** over anything that pins specific codes:
   `KEPT_566`, `HEADERS_32`, `ABSENT_6`, the GI cohort, the varicose families,
   the 45 singletons, and the QA0 chapter.
6. **Re-certify affected templates.** Any certified twin whose mapping names a
   code that changed status needs re-checking; a certification is a claim about
   a document under an edition, and the edition moved.

## ⚠️ TWO THINGS THAT WILL BREAK QUIETLY AND ARE NOT ON THE CRITICAL PATH

**1 · Stored `children` are a write-time snapshot (ruling #180).** Every
`header_use_billable_child` drop record written before the switch carries FY2026
descendants. After 2026-10-01 a stored list can name a code FY2027 deleted, and a
surface rendering it would tell a doctor to bill something that no longer exists.
A reader that can reach `billableDescendantsOf` should prefer a fresh derivation
from `code`. **Whether the record should carry an edition stamp is undecided and
owner-shaped** — it was filed with #180 and is not resolved here.

**2 · The gates pin FY2026's numbers and will pass anyway.** `74_719`, `23_467`,
`98_186`, `242_114`, `3096`, `45`, `6257` are hard-coded across
`icd10-fy2026-ingestion.test.ts`, `gate-billable-descendants.test.ts` and
`gate-r180-token-split.test.ts`. On FY2027 data they become wrong; on FY2026 data
they stay green. **Nothing tells you the edition is stale — the ingestion is what
tells you, and only if somebody runs it.**

## What would make this row dischargeable

`EDITIONS.fy2027` fully pinned, `--edition fy2027` passing its own assertions, the
FY2026→FY2027 status-change delta published, and the affected pins re-derived.
Until then this row stays open and **its date does not move**.
